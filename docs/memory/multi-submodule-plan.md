# Multi-submodule plan

Goal: robust multi-submodule support for polyglot superprojects (a few OR hundreds of submodules). Config was already ~80% there (per-buffer root scoping, per-root HEAD watchers + review-base store, memoized `git.root`). Work is consumer-side + lifecycle, NOT a redesign. A central repo registry was deliberately REJECTED (the three single-owner stores — `git.root_cache`, `git_head.watched`, the `review_base` map — already form an implicit registry; only *liveness* is unowned).

Branch: `feat/multi-submodule` (off main, 2026-06-28).

Staged plan (value/risk order): P1 superproject test fixture; P2 fix cwd-scoped breaks (diffview `<leader>gv`, review-base `<leader>gB`/`gX`); P3 re-key HEAD gate on resolved sha (detached SHA→SHA `git submodule update` + unborn-HEAD sentinel — `git_head.lua:32` currently gates on branch name only); P4 honor `data.root` in fan-out (add `git.buf_in_root`, exact-toplevel-equality not prefix); P5 bound HEAD fs-handles (`M.unwatch` via BufWipeout buffer-scan, evict on ENOENT) + swap `systemlist`→`vim.system():wait(timeout)` (timed-out resolve NOT cached); P6 async `git_head.check` (inline vim.system, single-flight+recheck, NO queue); P7 lazy `review_base.bootstrap`; P8 stale-cache invalidation (DirChanged + BufWritePost on .gitmodules) + wikilinks DRY.

User decision (2026-06-28): per-file git status INSIDE submodules in pickers/tree = ADD FULL RECURSION (a new stage, after P2) — aggregate status across all submodules; must be async + concurrency-bounded so hundreds of submodules don't freeze the UI (the picker's deliberate fixed-spawn design is what this relaxes). `git status` collapses a dirty submodule to one gitlink line, so per-submodule recursion is required.
