# Why Python LSP "go to definition / implementation" lands in the wrong place (state as of October 2026)

> A research note from October 2026, one of the sources for [the Python navigation research](README.md). It describes other editors and tools as of that date, and this config as it was before the switch to basedpyright.

Scope: root causes of inaccurate Python code navigation through LSP servers (pyright, basedpyright, Pylance for comparison, ty, pyrefly) in large multi-file projects, each with symptom, mechanism, detection and fix, ending with a troubleshooting checklist and defaults for a Neovim 0.11+ setup.

Version snapshot used for these notes (checked 2026-10-21): pyright latest release 1.1.414 (2026-09-09) ([pyright releases](https://github.com/microsoft/pyright/releases)); basedpyright v1.40.2 (2026-10-04) ([basedpyright releases](https://github.com/DetachHead/basedpyright/releases)); ty 0.0.90 (2026-10-20), beta since 2025-12-16 ([ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)); uv 0.13.5 (2026-10-21) ([uv changelog](https://github.com/astral-sh/uv/blob/main/CHANGELOG.md)). Where a claim comes from reading a server's source on its main branch rather than docs, it is labelled "(source code)".

## 1. Editable installs: why some break static import resolution, symptoms, fixes

### Takeaway
Only editable installs that use an executable import hook (a .pth line starting with `import` that installs a meta-path finder) are invisible to static servers. The premise that "uv's default" and hatchling do this is wrong: hatchling, PDM, poetry-core and `uv_build` all write path-based .pth files by default. The import-hook case is mainly setuptools ≥ 64 in its default "lenient" mode on a **flat layout or non-trivial package_dir mapping**. A simple src layout gets a static .pth even under setuptools. Fix it with `editable_mode=compat` or `strict`, by moving to a src layout or a path-based backend, or by pointing `extraPaths` at the source root.

### Cited Findings
- Pyright: "If you want to use static analysis tools with an editable install, you should configure the editable install to use .pth files that contain file paths rather than executable lines (prefixed with `import`) that install import hooks… because resolving module locations using an import hook requires executing Python code, they are not usable by Pyright and other static analysis tools… Pyright will be unable to find the corresponding source files." — [pyright import-resolution.md, "Editable installs"](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#editable-installs)
- Pyright docs: "Notably, setuptools uses import hooks by default"; for pip+setuptools use [compat mode](https://setuptools.pypa.io/en/latest/userguide/development_mode.html#legacy-behavior) or [strict mode](https://setuptools.pypa.io/en/latest/userguide/development_mode.html#strict-editable-installs); for uv+setuptools set `[tool.uv] config-settings = { editable_mode = "compat" }`; "The `uv_build` backend always uses path-based .pth files"; Hatchling "uses path-based .pth files by default. It will only use import hooks if you set `dev-mode-exact` to `true`"; PDM is path-based unless `editable-backend = "editables"`. — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#editable-installs). The uv/setuptools wording was added 2025-08-29 and 2025-09-04 ([doc commit history](https://github.com/microsoft/pyright/commits/main/docs/import-resolution.md)).
- Pyrefly documents the same matrix and adds "Poetry-core: always path-based". It warns that with import hooks Pyrefly "will be unable to automatically locate and analyze the corresponding source files". — [Pyrefly import resolution](https://pyrefly.org/en/docs/import-resolution/)
- setuptools strategy selection (source code): in its default mode, setuptools uses a static .pth (`_StaticPth`) only when `set(package_dir) == {""}` and the layout is "simple", i.e. src-layout-ish ("src-layout(ish) is relatively safe for a simple pth file"). Otherwise it uses `_TopLevelFinder`, which writes a finder module and a .pth containing `import __editable___<name>_finder; ….install()`, commented "Use a MetaPathFinder to avoid adding accidental top-level packages/modules". `strict` uses `_LinkTree`, a link farm under the build directory (build/\_\_editable\_\_.<name>-<tag>) added through a static .pth. — [setuptools editable_wheel.py](https://github.com/pypa/setuptools/blob/main/setuptools/command/editable_wheel.py)
- setuptools docs: strict mode is added in v64.0.0. `compat` "is *transitional* and will be removed in future versions of setuptools… offered 'as is'". setuptools "offers **no guarantee** of which technique will be used… may change depending on the specific version". — [setuptools development mode](https://setuptools.pypa.io/en/latest/userguide/development_mode.html). In source the removal is still undated ("TODO: Remove `compat` after Dec/2022", "TODO: define due_date") and the mode still works on main as of Oct 2026 — [editable_wheel.py](https://github.com/pypa/setuptools/blob/main/setuptools/command/editable_wheel.py)
- Strict-mode caveat from setuptools' own warning text: "New or renamed files may not be automatically picked up without a new installation." — [editable_wheel.py](https://github.com/pypa/setuptools/blob/main/setuptools/command/editable_wheel.py)
- Hatch docs: `dev-mode-dirs` overrides which directories are added to the search path, for example `["."]`. `dev-mode-exact` is a "more targeted mechanism" that "is not supported by static analysis tools & IDEs". — [Hatch build config, dev mode](https://hatch.pypa.io/latest/config/build/#dev-mode)
- uv: `uv_build` became the default backend for `uv init --package/--lib` in uv 0.8.0 (July 2025); it was hatchling before ([uv 0.8 changelog](https://github.com/astral-sh/uv/blob/main/changelogs/0.8.x.md)). Since uv 0.12.0 (2026-07-28), plain `uv init` declares a `uv_build` build system and puts code in a src layout, so the project is packaged by default ([uv 0.12 changelog](https://github.com/astral-sh/uv/blob/main/changelogs/0.12.x.md)). uv has `config-settings` and per-package `config-settings-package`, for example `{ numpy = { editable_mode = "compat" } }` ([uv settings](https://docs.astral.sh/uv/reference/settings/#config-settings)). Workspace members are installed editable: "Dependencies between workspace members are editable." ([uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/))
- ty (source code): its resolver reads static .pth files in site-packages to find editable roots and skips lines that start with `import ` or `import\t`. Import-hook editables are therefore not resolved by ty either. — [ty_module_resolver resolve.rs](https://github.com/astral-sh/ruff/blob/main/crates/ty_module_resolver/src/resolve.rs)
- Pyright (source code): when it asks the interpreter for search paths, it runs a script that dumps `sys.path` with no `-I` flag. In venvPath/venv mode it parses .pth files itself (`getPathsFromPthFiles`). Either way it only sees path entries, never meta-path finders. — [fullAccessHost.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/common/fullAccessHost.ts), [pythonPathUtils.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/analyzer/pythonPathUtils.ts)
- Pyright resolution order puts local code before site-packages: the execution-environment root, then `extraPaths`, then ./src when no execution environment is configured. Only after these does it try installed packages. — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#resolution-order)
- Debugging: set `verboseOutput: true` or pass `--verbose` for import-resolution logging — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#debugging-import-resolution-problems). The log lines include "Looking in root directory of execution environment", "Looking in extraPath", "Looking in python search path" and "Received N paths from interpreter" ([importResolver.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/analyzer/importResolver.ts), [fullAccessHost.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/common/fullAccessHost.ts)). Pyrefly: replace `check` with `dump-config` ([Pyrefly import resolution](https://pyrefly.org/en/docs/import-resolution/)). ty adds search-path info to unresolved-import diagnostics ([ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)).
- Community workaround (older, unverified on current setuptools): `export SETUPTOOLS_ENABLE_FEATURES=legacy-editable` before `pip install -e` — [CERN bamboo issue #100](https://gitlab.cern.ch/cp3-cms/bamboo/-/issues/100). Community report that the setuptools 64 change "broke static analysis tools" — [python-poetry/poetry#7583](https://github.com/python-poetry/poetry/issues/7583).

### Inferences
- **Catalogue row: import-hook editable.** *Symptom:* `reportMissingImports` ("Import X could not be resolved") on a first-party package that runs fine, so gd does nothing. A second variant: gd jumps to an old non-editable copy in site-packages when one is also installed. *Mechanism:* the finder is a runtime `sys.meta_path` entry; static servers only read `sys.path` and static .pth lines. *Detect:* `grep -l '^import' .venv/lib/python*/site-packages/*.pth` and look for `__editable__.*.pth` files plus `__editable___*_finder.py` modules. In pyright's verbose log the package's directory is missing from the received paths. *Fix (best first):* (a) use a path-based backend (`uv_build`, hatchling, pdm-backend, poetry-core) or a src layout with setuptools; (b) `pip install -e . --config-settings editable_mode=compat` or `strict`, or in uv `config-settings`/`config-settings-package`; (c) add the source root to `extraPaths`, or to an execution environment's `extraPaths`.
- The import-hook problem often does not show up for a single flat-layout project opened at its own root. Pyright finds the package through the execution-root step before it consults site-packages. It bites when the editable package lives outside the LSP root: a sibling monorepo member, a separate checkout, or a root that Neovim chose too deep. This follows from the documented resolution order.
- `strict` mode makes the server resolve into the link farm under build/. Depending on symlink handling, gd may open the build/... path rather than the real source file, and new files need a reinstall. I have not verified this; prefer `compat` or a path-based backend for editor use.
- "Jumps to the site-packages copy" without any hook: a regular (non-editable) install of a first-party package that the LSP root/extraPaths do not cover. Examples are `uv sync --no-editable`, `pip install .`, or a Docker image's venv. Pyright then legitimately resolves the installed copy. Fix by reinstalling editable or by making the source root visible locally (extraPaths/executionEnvironments).

### Gaps
- No primary statement found on whether Pylance does anything special for setuptools finder-based editables beyond pyright's documented behaviour.
- Not verified whether setuptools still honours `SETUPTOOLS_ENABLE_FEATURES=legacy-editable` in 2026 releases.
- How pyright presents paths through a strict-mode link farm (realpath vs link path) is unverified.

## 2. Stubs vs source: landing in .pyi files, and how to prefer source

### Takeaway
Pyright and basedpyright already split the two: if the client advertises `textDocument/declaration` support (Neovim does), **definition prefers .py source and declaration prefers .pyi stubs**. They fall back to whatever exists when the preferred kind is missing. So landing in a .pyi on `gd` usually means no source could be mapped: a C extension, a bundled or typeshed stub whose package is not installed in the configured environment, or a stub-only package. It is not a missing setting. ty and pyrefly behave the same way (definition → runtime .py, declaration/type-definition → stub). I found no Pylance command literally called "Go to Source Definition". Pylance's equivalent is the same definition/declaration split, shipped in 2021.2.1.

### Cited Findings
- Pyright (source code): `onDefinition` uses `DefinitionFilter.PreferSource` and `onDeclaration` uses `DefinitionFilter.PreferStubs` when `client.hasGoToDeclarationCapability` (set from `capabilities.textDocument?.declaration`). Otherwise both use `All`. `filterDefinitions` keeps only the preferred kind "unless filtering would produce an empty list". — [languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts), [definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts). basedpyright has the same logic — [basedpyright languageServerBase.ts](https://github.com/DetachHead/basedpyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- Pyright (source code): when the resolved declaration is in a stub, the `SourceMapper` looks up matching implementation declarations (`sourceMapper.findDeclarations`) or source modules and adds them as extra candidates. Overloaded functions add every overload's declaration. — [definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)
- Neovim's default client capabilities include `textDocument.declaration = { linkSupport = true }` and also `implementation` and `typeDefinition`. — [neovim runtime/lua/vim/lsp/protocol.lua](https://github.com/neovim/neovim/blob/master/runtime/lua/vim/lsp/protocol.lua)
- Pylance 2021.2.1: "Go-to-definition now brings you to source files (e.g. .py files), and a new 'go-to-declaration' option brings you to stub files (.pyi). If either would otherwise return no result, Pylance will bring you to whichever files are available." — [pylance-release 2021.2.1](https://github.com/microsoft/pylance-release/releases/tag/2021.2.1)
- Pyright resolution order for installed packages: a `-stubs` package first, then an inline .pyi in the package, then py.typed .py files, then library .py if `useLibraryCodeForTypes` (default true). After those come stdlib typeshed and then third-party typeshed stubs bundled with pyright. — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#resolution-order). `reportMissingModuleSource` (default "warning") fires when "a type stub is found, but the module source file was not found" — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)
- Pylance bundled stubs (older, 2021–2022 context): users complained that bundled stubs caught gd. Jake Bailey (Microsoft): "we fully intend that things will work with the stubs present". Eric Traut: bundled typeshed stubs "are resolved last in PEP 561 ordering". A user reported Pylance switched from bundling django-stubs to django-types around Oct 2022. Workarounds at the time included deleting bundled stub folders (community). — [pylance-release discussion #2663](https://github.com/microsoft/pylance-release/discussions/2663)
- Pyrefly: "If there is both a .pyi and .py file, we will jump to the .py" for go to definition. Go to type definition goes to the .pyi when both exist. Go to declaration "stops at imports". — [Pyrefly IDE features](https://pyrefly.org/en/docs/IDE-features/). Pyrefly's bundled third-party stubs follow special rules: with no config file and the package installed, bundled stubs are used, and so on. — [Pyrefly import resolution](https://pyrefly.org/en/docs/import-resolution/)
- ty: "Go to Declaration: Navigate to the declaration site of a symbol, which can differ from its definition (could be in a stub file)" — [ty language server features](https://docs.astral.sh/ty/features/language-server/). The ty changelog records: prefer the runtime definition, not the stub, for classes and functions (0.0.1-alpha.16); jump to runtime stdlib definitions rather than typeshed (alpha.18); "Follow aliases when attempting to map a definition in a stub file to its 'real' runtime definition" (0.0.40, 2026-05-27). — [ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)
- Pyright has a `stubPath` (default ./typings) for custom stubs. It is searched first in the resolution order. — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md), [import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)

### Inferences
- **Catalogue row: gd lands in .pyi.** *Mechanisms:* (1) the client did not advertise declaration capability (not the case for stock Neovim, but possible with a custom `capabilities` table that drops `textDocument.declaration`); (2) no source exists: a C extension, a compiled or zipped wheel, or typeshed stdlib for C modules; (3) the package is not installed in the environment pyright uses, so only bundled typeshed or `-stubs` content exists. The `reportMissingModuleSource` warning on the import line confirms this; (4) a stub in `stubPath`/typings shadows a library and the source mapper finds no counterpart. *Detect:* the import line shows a `reportMissingModuleSource` warning, or `:lua vim.lsp.buf.declaration()` and `definition()` return the same .pyi. *Fix:* install the real package into the configured interpreter; fix the interpreter (section 6); remove stale stubs from typings; use `gD` (declaration) deliberately when you want the stub.
- A custom `capabilities` built with `vim.lsp.protocol.make_client_capabilities()` (or blink/cmp's merge helpers) keeps `declaration`. Only hand-built tables risk losing it. This is my reading of the pyright logic above.
- Generated stubs (mypy-protobuf .pyi next to _pb2.py, stubgen output) follow the same rule. With PreferSource, gd should prefer the generated .py when it exists. Not verified for protobuf specifically.

### Gaps
- I could not confirm a separate "Go to Source Definition" command in Pylance as of 2026, and found no Pylance setting that disables bundled stubs.
- No primary source on how pyright's source mapper treats `-stubs` packages whose runtime package is a compiled extension, other than "falls back to stubs".

## 3. Re-exports and indirection (`__init__` re-exports, `__all__`, star imports, aliases, lazy `__getattr__`, conditional imports)

### Takeaway
Pyright-family servers follow alias chains through re-exports to the final declaration, including privately re-exported names. Star imports follow `__all__` when it uses the supported idioms. `TYPE_CHECKING` blocks are analysed and their `else` branches are not. Module-level `__getattr__` lazy loading is opaque unless a .pyi stub lists the names. Conditional definitions can yield several targets. Wrong `pythonVersion`/`pythonPlatform` can make the branch you care about "unreachable", and then it has no navigation at all.

### Cited Findings
- Pyright (source code): definitions are built by `evaluator.resolveAliasDeclaration(decl, /* resolveLocalNames */ true, { allowExternallyHiddenAccess: true })` for each declaration. Aliases are followed through re-exports even when the re-export is "private" by py.typed rules. If an alias resolves to a module, it falls back to the submodule. — [definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)
- Pyright models two loader side effects: `import a.b.c` makes `a`, `a.b` and `a.b.c` available, and in \_\_init\_\_.py, `from .a import b` also binds submodule `a`. All other side effects are "intentionally *not* modeled". One example is relying on another module's `import a.b` to make `a.b` reachable. — [pyright import-statements.md](https://github.com/microsoft/pyright/blob/main/docs/import-statements.md)
- Re-export visibility rules for py.typed packages: imported symbols are private unless written `import A as A`, `from X import A as A`, `from . import A`, a wildcard, or listed in `__all__`. The supported `__all__` idioms are `=`, `+=`, `.extend`, `.append`, `.remove` and `+= submodule.__all__`. — [pyright typed-libraries.md](https://github.com/microsoft/pyright/blob/main/docs/typed-libraries.md). `reportUnsupportedDunderAll` (default warning) flags `__all__` manipulation "not allowed by a static type checker, thus rendering the contents of `__all__` to be unknown or incorrect" — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)
- Static conditions pyright evaluates: `sys.version_info` comparisons, `sys.platform ==`, `os.name ==`, `TYPE_CHECKING`, `True/False`, `defineConstant` identifiers, and `not/and/or` of these. Code under a statically false condition is not analysed: "language server features like completion suggestions are not available for this code". `if not TYPE_CHECKING:` is unreachable. — [pyright type-concepts-advanced.md](https://github.com/microsoft/pyright/blob/main/docs/type-concepts-advanced.md#static-conditional-evaluation). `TYPE_CHECKING` "has a value of False within the Python runtime but a value of True when the type checker is performing its analysis" — [pyright typed-libraries.md](https://github.com/microsoft/pyright/blob/main/docs/typed-libraries.md)
- Lazy loading through PEP 562 module `__getattr__`: "static type checkers (such as mypy and pyright) will not be able to infer the types of lazy-loaded modules and functions" and IDEs "won't provide code completion". The recommended fix is an \_\_init\_\_.pyi listing the imports (with `x as x` or `__all__`), loaded at runtime through `lazy_loader.attach_stub`. "Type stubs are ignored at runtime, but used by static type checkers." — [Scientific Python SPEC 1](https://scientific-python.org/specs/spec-0001/)
- PEP 810 (explicit `lazy import` syntax) was accepted by the Steering Council — [PEP 810](https://peps.python.org/pep-0810/), [discussion](https://discuss.python.org/t/pep-810-explicit-lazy-imports/104131).
- Pyright option `reportIncompleteStub` covers a module-level `__getattr__` in a stub, "indicating that it is incomplete" — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)

### Inferences
- **Catalogue row: gd stops at a re-export or the wrong module.** In pyright it normally does not stop there. If gd lands on an \_\_init\_\_.py line, the name probably resolves to a module (the submodule fallback goes to line 0 of the module) or to a non-import assignment such as `Foo = _impl.Foo` or `Foo = getattr(mod, "Foo")`. Assignment-based aliases are variable declarations, so gd goes to the assignment, not the class. *Fix:* use `from .impl import Foo as Foo` or `__all__` instead of assignments.
- **Catalogue row: lazy `__getattr__` package (common in scientific libraries).** *Symptom:* symbols show as `Any`/Unknown and gd goes nowhere or to `__getattr__`. *Fix:* ship or vendor an \_\_init\_\_.pyi with explicit re-exports (SPEC 1 pattern). For your own code, add `if TYPE_CHECKING: from .sub import X` next to the lazy `__getattr__`.
- **Catalogue row: try/except ImportError or version-gated imports.** Pyright collects every declaration of the symbol, so gd may present several targets (Neovim 0.11+ shows a quickfix/location list). If the configured `pythonVersion`/`pythonPlatform` is wrong (wrong interpreter, see section 6), the branch you expect is "unreachable" and its names are not navigable. *Detect:* the code is greyed out as unreachable. *Fix:* point the server at the right interpreter or set `pythonVersion`/`pythonPlatform`/`defineConstant`.
- How servers will treat PEP 810 `lazy import` syntax is unknown to me (see Gaps). Expect a gd-ignored-module symptom only if a server does not parse the new syntax.

### Gaps
- No source found on pyright, basedpyright, ty or pyrefly support for PEP 810 `lazy import` syntax as of Oct 2026.
- No primary documentation found on how ty and pyrefly treat module `__getattr__`, or on multiple-declaration results for conditional imports.

## 4. Dynamic dispatch: ABCs, Protocols, mixins, overrides; definition vs implementation

### Takeaway
Go to definition is static: it resolves the member on the **declared or inferred type of the receiver**. A call through a base-class, ABC or Protocol-typed variable therefore goes to the base or abstract method by design. Finding concrete overrides needs `textDocument/implementation` or type hierarchy. As of Oct 2026, **pyright does not implement either**. basedpyright ≥ 1.34.0 (2025-11-19) implements `textDocument/implementation`, covering overrides, subclasses and Protocol structural implementors. ty implements implementation (0.0.64, 2026-07-27) and type hierarchy (0.0.20, 2026-03-02). Pyrefly lists both. Pylance added Go to Implementation in Feb 2025. If the receiver's type is Unknown (untyped parameter), nothing navigates.

### Cited Findings
- Pyright (source code, main): the server advertises `definitionProvider`, `declarationProvider`, `typeDefinitionProvider`, `referencesProvider`, `callHierarchyProvider` and others. It has **no `implementationProvider` and no `typeHierarchyProvider`**. — [pyright languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts). An older user report shows Neovim saying "method textDocument/implementation is not supported" with pyright 1.1.184 — [Neovim discourse (2021)](https://neovim.discourse.group/t/pyright-go-to-implementation-not-working/1336)
- basedpyright: "basedpyright supports 'Go to Implementations' / 'Find All Implementations' from pylance" — [basedpyright Pylance features](https://github.com/DetachHead/basedpyright/blob/main/docs/benefits-over-pyright/pylance-features.md). The PR finds "all overrides of that method or class attribute", "all subclasses" when used on a class, and "works with Protocols" (structural match: a class whose `foo` signature does not match the protocol is excluded). The author says "For a big project it is kind of slow… There's no way to find all subclasses without searching every file in the project." — [basedpyright PR #1636](https://github.com/DetachHead/basedpyright/pull/1636), shipped in [v1.34.0](https://github.com/DetachHead/basedpyright/releases/tag/v1.34.0) (2025-11-19). basedpyright advertises `implementationProvider` but not type hierarchy (source code) — [basedpyright languageServerBase.ts](https://github.com/DetachHead/basedpyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- Pylance: "Pylance now has support for Go to Implementation… navigate to the implementation of a function or method directly from its usage… particularly helpful when working with inherited classes." — [VS Code Python, February 2025 release](https://devblogs.microsoft.com/python/python-in-visual-studio-code-february-2025-release/)
- ty: "Go to Implementation: Find known implementations of a class or class member, including subclasses and method overrides". Call hierarchy and type hierarchy are both marked supported. — [ty language server](https://docs.astral.sh/ty/features/language-server/). Changelog: "Implement LSP `textDocument/implementation` request" (0.0.64, 2026-07-27); "Add support for the LSP protocol's 'type hierarchy' feature" (0.0.20, 2026-03-02); "Parallelize subtype hierarchy search" (later). — [ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)
- Pyrefly: "Go to implementation: on a method, navigate to all reimplementations"; "Type Hierarchy: See all subclasses and superclasses of a selected class"; call hierarchy is supported too. — [Pyrefly IDE features](https://pyrefly.org/en/docs/IDE-features/)
- Neovim: 0.11 added default `gri` → `vim.lsp.buf.implementation()` ([news-0.11](https://neovim.io/doc/user/news-0.11.html)), and 0.12 added `grt` → `vim.lsp.buf.type_definition()` ([news](https://neovim.io/doc/user/news.html)). `vim.lsp.buf.typehierarchy("subtypes"|"supertypes")` exists ([lsp.txt](https://neovim.io/doc/user/lsp.html#vim.lsp.buf.typehierarchy())). In 0.11, definition/declaration/type_definition/implementation/references "now support merging the results of multiple clients" ([news-0.11](https://neovim.io/doc/user/news-0.11.html)).
- Unknown receivers (pyright type inference): unannotated parameters are Unknown unless inferred. Exceptions: `self`/`cls`; a parameter "inherits" the annotation from a same-named base-class method with the same signature, no overloads and annotated params; inference from a default value (`None` → `Unknown | None`). Call-site return type inference runs only when *all* parameters are unannotated, and "Pyright limits this recursion to a small number". — [pyright type-inference.md](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md)
- Pyright `reportImplicitOverride` (off in every mode) flags overrides missing `@override`. basedpyright autocompletion inserts `@override` automatically (3.12+ or with `useTypingExtensions`). — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md), [basedpyright LS improvements](https://github.com/DetachHead/basedpyright/blob/main/docs/benefits-over-pyright/language-server-improvements.md)

### Inferences
- **Catalogue row: gd goes to the abstract or base method.** *Mechanism:* static receiver type (base, ABC, Protocol, or a mixin's `self`). This is correct LSP behaviour, not a bug. *Detect:* hover the receiver and see a base or Protocol type. *Fix:* use `gri` on a server that supports it (basedpyright, ty, pyrefly). On plain pyright, use `grr` (references) on the base method, or incoming call hierarchy. Narrow the type at the call site (`isinstance`, a concrete annotation) if gd should be exact.
- **Catalogue row: gd does nothing on `obj.method()`.** *Mechanism:* `obj` is Unknown (untyped parameter, untyped container element, untyped decorator or factory return), so there is no class to look the member up on. *Detect:* hover shows `Unknown`/`Any`; basedpyright `reportUnknownMemberType`/`reportAny` would flag it. *Fix:* annotate the parameter or the factory's return. `type[T] -> T` generics for factories/registries make results navigable.
- Mixins: methods called on `self` inside a mixin resolve against the mixin's own type, so a method provided by a sibling base is "unknown attribute" with no navigation. A `Protocol` self-type annotation (`def m(self: HasFoo)`) or a typed base restores it. This is a common typing pattern; I found no maintainer statement on it in this research.
- With two Python servers attached (for example pyright plus ty), Neovim 0.11+ merges both servers' gd results, so duplicate or conflicting locations appear in a list. Disable navigation on one of them (for example `pyright.disableLanguageServices` or not enabling the second).

### Gaps
- No primary statement from pyright maintainers in this research saying implementation/type hierarchy will never be added. The finding is only that main does not advertise them.
- No benchmark of basedpyright/ty/pyrefly implementation search latency on large repos, beyond the PR author's "kind of slow".

## 5. Metaprogramming: decorators, descriptors, dataclasses/attrs/Pydantic/SQLAlchemy/Django, DI, registries, getattr dispatch

### Takeaway
Pyright-family servers have no plugin system by design. Anything a mypy plugin used to synthesise has to be expressed in the type system itself: `dataclass_transform` (PEP 681), `ParamSpec` (PEP 612), `@overload`, Protocols, `Mapped[...]`. Fully unannotated decorators are treated as identity by pyright. Partially typed ones (`-> Callable`) erase the signature. String- or getattr-based dispatch, DI lookups by string key and plugin registries are not statically resolvable unless their APIs are typed generically.

### Cited Findings
- "Pyright maintainers have made the decision not to support plug-ins because of their many downsides: discoverability, maintainability, … security, performance (especially latency — which is critical for language servers), and robustness. Instead, we have taken the approach of working with the typing community and library authors to extend the type system… An example of this is PEP 681, which introduced `dataclass_transform`." — [pyright mypy-comparison.md](https://github.com/microsoft/pyright/blob/main/docs/mypy-comparison.md#plugins)
- Pyright (source code) in decorators.ts: "If the decorator is completely unannotated and the return type includes unknowns, assume that it preserves the type of the input function". This applies only when no parameter of the decorator is annotated and it has no declared return type. — [decorators.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/analyzer/decorators.ts)
- `reportUntypedFunctionDecorator` / `reportUntypedClassDecorator` flag decorators "that have no type annotations. These obscure the function type, defeating many type analysis features". They are "error" in strict and "none" in other modes. — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md). The typed-libraries guide gives "Function with partially unknown type (because type is obscured by untyped decorator)" as an example — [typed-libraries.md](https://github.com/microsoft/pyright/blob/main/docs/typed-libraries.md)
- typeshed types `functools.wraps(...)` as returning `_Wrapped[_PWrapped, _RWrapped, _PWrapper, _RWrapper]` whose `__call__(self, *args: _PWrapper.args, **kwargs: _PWrapper.kwargs) -> _RWrapper`. The decorated object therefore takes the **wrapper's** signature, not the wrapped function's. — [typeshed functools.pyi](https://github.com/python/typeshed/blob/main/stdlib/functools.pyi)
- Pydantic: editor support "works by making use of the `@dataclass_transform` decorator" and "Pylance will treat your Pydantic models as if they were Python's pure dataclasses". Limitation: pyright needs `default=` as a keyword in `Field(...)`; "a limitation of dataclass transforms and cannot be fixed in pydantic". — [Pydantic VS Code integration](https://pydantic.dev/docs/validation/latest/integrations/dev-tools/visual_studio_code/)
- SQLAlchemy: "The SQLAlchemy Mypy Plugin is DEPRECATED, and will be removed in the SQLAlchemy 2.1 release"; it "works only up until mypy version 1.10.1"; Pylance/pyright "cannot make use of Mypy plugins". SQLAlchemy 2.0's declarative typing (`Mapped[...]`) is "fully pep-484 compliant" and "removes the need for the Mypy plugin". — [SQLAlchemy mypy extension docs](https://docs.sqlalchemy.org/en/20/orm/extensions/mypy.html)
- Django: django-types is a fork of django-stubs without the mypy plugin, aimed at pyright. Managers must be declared explicitly, for example `objects = Manager["User"]()`, because the base Model does not define `objects`. — [django-types on PyPI](https://pypi.org/project/django-types/). A user reported that Pylance bundles django-types instead of django-stubs (Oct 2022) — [pylance-release discussion #2663](https://github.com/microsoft/pylance-release/discussions/2663)
- basedpyright has a doc on `dataclass_transform` improvements — [basedpyright dataclass-transform.md](https://github.com/DetachHead/basedpyright/blob/main/docs/benefits-over-pyright/dataclass-transform.md) (exists in repo; contents not reviewed here).
- ty: "Pydantic: Recognize models installed on extra search paths" (changelog), which shows ty special-cases or understands Pydantic models — [ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)
- Specs: [PEP 681 dataclass_transform](https://peps.python.org/pep-0681/), [PEP 612 ParamSpec](https://peps.python.org/pep-0612/).

### Inferences (catalogue rows)
- **Untyped or partially typed decorator.** *Symptom:* gd on the decorated name works, because it is a declaration, but calls return Unknown, so navigation on the *result* fails. A decorator annotated `(f: Callable) -> Callable` loses the signature entirely. A `functools.wraps` wrapper typed `(*args, **kwargs)` without annotations gives `(*args, **kwargs) -> Unknown`. *Fix:* `def deco(f: Callable[P, R]) -> Callable[P, R]` with `ParamSpec`. For signature-changing decorators use `Concatenate` and explicit return types. Turn on `reportUntypedFunctionDecorator` to find offenders.
- **Dataclass-like frameworks** (attrs, Pydantic, SQLAlchemy `MappedAsDataclass`, msgspec): navigation on fields works when the library uses `dataclass_transform` and annotated fields. Generated `__init__` parameters map to the field declarations. Old attrs/SQLAlchemy 1.x patterns (`Column(...)` without `Mapped`) give Unknown attributes. Fix: SQLAlchemy 2.0 `Mapped[T]` + `mapped_column`, and attrs' modern `@define` API (attrs supports `dataclass_transform`; general knowledge, not re-verified here).
- **Django ORM:** reverse relations, `objects` and dynamic `QuerySet` methods are synthesised by metaclasses and the django-stubs mypy plugin. Without a plugin, pyright only sees what django-types declares plus your explicit annotations (`objects: ClassVar[Manager["X"]]`, explicit `RelatedManager` annotations). Expect gd on `Model.objects.filter` to land in stub/manager code, not in model-specific code.
- **Properties/descriptors:** gd on `obj.prop` goes to the property or descriptor declaration in the class, which is usually what users want. Descriptors without typed `__get__` return Unknown, which kills navigation on the result.
- **DI containers, plugin registries, `getattr(obj, name)()` dispatch, string-keyed handlers:** not statically resolvable. A typed facade restores navigation: `def resolve(self, cls: type[T]) -> T`, `@overload` per `Literal` key, a `Protocol` for plugin interfaces (then use `gri` on basedpyright/ty/pyrefly to list implementors), or `TypedDict`/`Literal` maps. Class-level `__getattr__` makes every unknown attribute "valid" with its return type, which hides missing navigation instead of fixing it.

### Gaps
- No primary source reviewed on dependency-injection libraries (dependency-injector, punq, lagom) and pyright navigation.
- Did not verify how ty and pyrefly handle unannotated decorators (whether they use a pyright-like identity rule).

## 6. Project and environment shape: interpreter, monorepos, src layout, namespace packages, execution environments, LSP root, generated code

### Takeaway
Most "wrong place" reports reduce to the server analysing a different project than the one you think. It may have the wrong interpreter or venv (so it gets the wrong site-packages, wrong `pythonVersion` and static branches, or installed copies instead of source). It may have the wrong root (Neovim's `root_markers` pick the nearest pyproject.toml in a monorepo member). Or it may resolve to a local namespace directory, which pyright ranks *below* a regular package in site-packages. Execution environments plus `extraPaths` (with globs since pyright 1.1.414) are the pyright-family fix. ty and pyrefly have their own root/search-path settings.

### Cited Findings
- Pyright interpreter selection, in priority order: (1) `venvPath` + `venv`; (2) `python.pythonPath` setting; (3) "the default Python environment (i.e. the one that is invoked when typing `python` in the shell)". — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#configuring-your-python-environment). `venvPath`/`venv` in a shared config is discouraged because paths differ per developer — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)
- basedpyright: "if neither `pythonPath` or `venvPath`/`venv` are set, basedpyright will check for a venv at ./.venv and if it finds one, it will use its python interpreter". — [basedpyright better defaults](https://github.com/DetachHead/basedpyright/blob/main/docs/benefits-over-pyright/better-defaults.md). basedpyright also has `basedpyright.analysis.configFilePath` for configs in a subdirectory ("useful for monorepo structures"), with a Neovim example — [basedpyright LS settings](https://github.com/DetachHead/basedpyright/blob/main/docs/configuration/language-server-settings.md)
- ty environment discovery order: `VIRTUAL_ENV`, an active non-base Conda env, `.venv` in the project root, Conda base, then `python3`/`python` on PATH. First-party search paths are ./src, ./<project-name> (only if ./<project-name>/<project-name> exists) and ./python, all before the project root. Otherwise use `environment.root`. `PYTHONPATH` entries go after `extra-paths` and before site-packages. — [ty modules](https://docs.astral.sh/ty/modules/). The ty changelog adds "Discover uv workspace roots" (0.0.64) and "Only add ./src as a search path if ./src/\_\_init\_\_.py(i) does not exist", and removes `src.root` in favour of `environment.root` — [ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)
- Pyrefly: the search path comes from CLI/config. Unless `disable-search-path-heuristics` is set, an import root is appended: src/ beside the config, or the parent if the config dir has \_\_init\_\_.py, or else the config dir. A fallback search path covers sibling dirs such as tests/. Site packages come from the config or from "Filtered entries from a Python interpreter's `sys.path`". — [Pyrefly import resolution](https://pyrefly.org/en/docs/import-resolution/)
- Pyright src layout: "If no execution environment is configured, try to resolve using the local directory `src`" (`autoSearchPaths`, on by default in lspconfig) — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md), [pyright settings.md](https://github.com/microsoft/pyright/blob/main/docs/settings.md), [nvim-lspconfig pyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyright.lua)
- Execution environments: each has a `root` and optional `extraPaths` that "overrides the default extraPaths". "each file's execution environment mapping is independent, so if file A is in one execution environment and imports a second file B within a second execution environment, any imports from B will use the extraPaths in the second execution environment." — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md#execution-environment-options)
- `extraPaths` glob expansion (`*`, `**`, `?`) applies to the top-level, per-execution-environment and `python.analysis.extraPaths` settings. Only directories match, the expanded order is deterministic, explicit entries win on duplicates, and the doc example is `["libs/shared/src", "libs/*/src"]`. — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md#extra-path-glob-expansion). First appears in the docs at tag 1.1.414 (absent at 1.1.413) — [1.1.414 doc](https://github.com/microsoft/pyright/blob/1.1.414/docs/import-resolution.md) vs [1.1.413 doc](https://github.com/microsoft/pyright/blob/1.1.413/docs/import-resolution.md). Present in basedpyright docs at v1.40.1 — [basedpyright v1.40.1 import-resolution](https://github.com/DetachHead/basedpyright/blob/v1.40.1/docs/usage/import-resolution.md)
- Pyright namespace-package ranking (source code), `_pickBestImport`: "Prefer traditional packages over namespace packages" (the candidate whose first resolved path is non-empty wins), then "Prefer local over third-party", then "Prefer py.typed over non-py.typed". An unresolved namespace package is assumed to be a partial stub package, and searching continues "for a real package". — [importResolver.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/analyzer/importResolver.ts)
- Pyright last-resort resolution: "attempt to import a module from the same directory as the importing file and parent directories that are also children of the root workspace" — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)
- Neovim root selection: lspconfig's pyright and basedpyright `root_markers` are `pyrightconfig.json, pyproject.toml, setup.py, setup.cfg, requirements.txt, Pipfile, .git`. ty uses `ty.toml, pyproject.toml, setup.py, setup.cfg, requirements.txt, .git` and pyrefly `pyrefly.toml, pyproject.toml, …, .git`. — [lsp/pyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyright.lua), [lsp/basedpyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/basedpyright.lua), [lsp/ty.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/ty.lua), [lsp/pyrefly.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyrefly.lua). `vim.fs.root` evaluates each marker item in order against all ancestors until a match. Nested lists `{ { 'a', 'b' }, '.git' }` mean "equal priority". — [Neovim vim.fs.root docs](https://neovim.io/doc/user/lua.html#vim.fs.root())
- nvim-lspconfig's pyright and basedpyright configs define a buffer command `:LspPyrightSetPythonPath` that updates `settings.python.pythonPath` and sends `workspace/didChangeConfiguration`. The basedpyright config deliberately leaves `useLibraryCodeForTypes` unset so project config can override it. — [lsp/pyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyright.lua), [lsp/basedpyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/basedpyright.lua)
- uv workspaces share a root, and members depend on each other editably — [uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/)
- Pants: `pants roots` gives source roots; Pants suggests writing them into a .env PYTHONPATH for VS Code, `pants export --resolve=…` for venvs (`--export-py-editable-in-resolve` for first-party editables), and `pants export-codegen ::` to dist/codegen for generated protobuf/gRPC code ("you will have to manually rerun this goal"). — [Pants: setting up an IDE](https://www.pantsbuild.org/stable/docs/using-pants/setting-up-an-ide)
- Pyright `useLibraryCodeForTypes` (default true) controls whether library .py files are parsed when there are no stubs. Without it, unstubbed libraries are Unknown. — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)

### Inferences (catalogue rows)
- **Wrong interpreter.** *Symptoms:* everything third-party unresolved, gd into a global or system site-packages copy, or version-gated code greyed out. *Mechanism:* pyright falls back to `python` on Neovim's PATH (nvim started outside the venv). basedpyright and ty look for .venv only at *their* project root. *Detect:* pyright verbose log "Executing interpreter" and "Received N paths from interpreter", or hover a stdlib/3rd-party symbol and check the path. *Fix:* start nvim from an activated venv or `uv run nvim`; or set `python.pythonPath` per root (`:LspPyrightSetPythonPath`, or a `before_init` that finds .venv upward); or set `venvPath`/`venv` in a per-user config.
- **Monorepo root too deep (uv workspace or poetry multi-project).** *Symptom:* cross-package gd lands in site-packages or fails, find-references misses other members, and several pyright instances run (one per member). *Mechanism:* the flat `root_markers` list matches the nearest member pyproject.toml before .git. basedpyright's ./.venv check is then relative to the member, while uv puts the single .venv at the workspace root, so it falls back to PATH python. *Fix:* prefer a workspace-level marker, for example `root_markers = { 'pyrightconfig.json', 'uv.lock', { 'pyproject.toml', 'setup.py', 'setup.cfg' }, '.git' }`. Then put a pyrightconfig.json or `[tool.pyright]` at the workspace root with `executionEnvironments` per member, or `extraPaths` globs such as "packages/*/src" (pyright ≥ 1.1.414, basedpyright ≥ 1.40.1).
- **Root too shallow (repo root above the Python project).** *Symptom:* the config in backend/pyproject.toml is ignored and ./src is not added. *Fix:* basedpyright `configFilePath`, or a pyrightconfig.json at the root with `executionEnvironments` `{ root = "backend/src" }`.
- **Local namespace directory shadowing.** *Symptom:* gd on `import company.lib` lands in the site-packages copy, or a module "can't be found" even though the folder is in the repo. *Mechanism:* a directory without \_\_init\_\_.py is a namespace package, and pyright prefers a regular package (one with \_\_init\_\_.py) from site-packages over it. A stray local dir named like a dependency (a tests/ or scripts/ folder, or a partial checkout) can also capture names. *Detect:* verbose log, plus the presence of \_\_init\_\_.py. *Fix:* add \_\_init\_\_.py where the package is not meant to be a namespace; uninstall stale non-editable copies; for intentional PEP 420 namespaces split across repos, make sure every portion is on the search path (editable path .pth or `extraPaths`).
- **Generated code** (protobuf, OpenAPI clients, Pants or Bazel outputs): gd fails until the output directory is on the search path. Add it to `extraPaths` (or ty `extra-paths`, pyrefly `search-path`), or rely on Pants `export-codegen` and re-run it after regeneration. For Pants and Bazel, translate the tool's source roots into `extraPaths`. Note that pyright queries `sys.path` from the interpreter without `-I` (source code), so a `PYTHONPATH` exported into Neovim's environment is likely to reach pyright too. This is inferred from fullAccessHost.ts and not tested.

### Gaps
- No primary source found for Bazel (rules_python, aspect rules_py) IDE/pyright guidance in this research.
- No maintainer guidance found comparing "one LSP instance at the monorepo root" against "one per member" for pyright performance.
- Did not verify whether ty or pyrefly rank namespace packages below regular site-packages packages the way pyright does. ty changelog shows ongoing namespace work (legacy `pkg_resources`/`pkgutil` namespaces, partial-stub namespace fixes).

## 7. Type-annotation coverage vs navigation quality, and tools to raise it

### Takeaway
I found no published measurement that links annotation coverage to navigation accuracy. The mechanism is direct, though: member navigation needs a known receiver type, and Unknown propagates. The practical approach is to measure Unknowns with the type checker (pyright `--verifytypes` completeness score for libraries; strict-mode `reportUnknown*` and basedpyright `reportAny` for apps; basedpyright baselines to adopt incrementally). Then raise coverage with inference tools (pyrefly `infer`, MonkeyType, RightTyper, inlay-hint insertion) and review the output by hand.

### Cited Findings
- `pyright --verifytypes <lib>` "will analyze the library, identify all symbols that comprise the interface… and emit errors for any symbols whose types are ambiguous or unknown. It also produces a 'type completeness score' which is the percentage of symbols with known types". It can be combined with `--outputjson` and `--ignoreexternal`. It needs a py.typed package installed in a clean env. — [pyright typed-libraries.md](https://github.com/microsoft/pyright/blob/main/docs/typed-libraries.md), [command-line.md](https://github.com/microsoft/pyright/blob/main/docs/command-line.md)
- Pyright's `reportUnknownParameterType`, `reportUnknownArgumentType`, `reportUnknownLambdaType`, `reportUnknownVariableType` and `reportUnknownMemberType` are "none" in off/basic/standard and "error" in strict. `reportMissingTypeStubs` is "error" only in strict. — [pyright configuration.md defaults table](https://github.com/microsoft/pyright/blob/main/docs/configuration.md#diagnostic-settings-defaults)
- basedpyright adds `reportAny` ("accounts for all scenarios not covered by the `reportUnknown*` rules"), `reportExplicitAny`, `reportMissingParameterType`, and `allowedUntypedLibraries` to exempt specific modules. Its default `typeCheckingMode` is "recommended", which "enables all diagnostic rules as either 'warning' or 'error'". — [basedpyright config-files.md](https://github.com/DetachHead/basedpyright/blob/main/docs/configuration/config-files.md). `basedpyright.analysis.baselineMode` controls the baseline file for incremental adoption — [basedpyright LS settings](https://github.com/DetachHead/basedpyright/blob/main/docs/configuration/language-server-settings.md)
- basedpyright supports double-clicking (inserting) inlay hints, including on Callable types — [basedpyright Pylance features](https://github.com/DetachHead/basedpyright/blob/main/docs/benefits-over-pyright/pylance-features.md)
- Pyright checks unannotated code by default ("important for language server features"), unlike mypy, which skips unannotated functions unless `--check-untyped-defs` is set. — [pyright mypy-comparison.md](https://github.com/microsoft/pyright/blob/main/docs/mypy-comparison.md)
- Pyrefly `pyrefly infer` adds annotations for parameters, return types and containers. It is "under active development", and the docs recommend small batches and manual review because new annotations can introduce new errors. — [Pyrefly autotype](https://pyrefly.org/en/docs/autotype/)
- MonkeyType collects runtime argument and return types and can generate stubs or apply draft annotations — [MonkeyType on PyPI](https://pypi.org/project/MonkeyType/). RightTyper combines runtime sampling with static analysis. Its paper reports about 27% overhead and criticises MonkeyType slowdowns of up to 270× — [RightTyper paper (arXiv 2507.16051)](https://arxiv.org/abs/2507.16051). The project's own benchmark claim is "monkeytype runs 40x slower… righttyper… under 3% slower" (self-reported) — [righttyper on PyPI](https://pypi.org/project/righttyper/)
- Pyright inference aids that reduce Unknowns without annotations: call-site return type inference, parameter inheritance from base-class methods, default-value inference, and `strictListInference`/`strictDictionaryInference`/`strictSetInference` (default false) that avoid `list[Unknown]` for mixed literals. — [pyright type-inference.md](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md), [configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)

### Inferences

#### Consolidated troubleshooting checklist (synthesis of sections 1–7)
1. **Which server answered?** `:checkhealth vim.lsp` / `:LspInfo`. If more than one Python server is attached, Neovim 0.11+ merges gd results. Keep one navigation provider (for example pyright `disableLanguageServices`, or do not enable the second).
2. **Which root?** Check `vim.lsp.get_clients({bufnr=0})[1].config.root_dir`. In monorepos expect the nearest member pyproject.toml. Fix root_markers or add a root pyrightconfig.json.
3. **Which interpreter?** Set `verboseOutput` (or `python.analysis.logLevel = "Trace"`) and read `:LspLog` for "Executing interpreter…/Received N paths". Compare with `uv run python -c "import sys; print(sys.prefix)"`.
4. **Does the import resolve to the file you expect?** Verbose log lines "Looking in root directory…/extraPath…/python search path…", plus a `reportMissingImports`/`reportMissingModuleSource` diagnostic on the import.
5. **Editable install kind:** grep site-packages .pth files for `import` lines (`__editable__` finders). Switch to compat/strict, a path-based backend or src layout, or add extraPaths.
6. **Stale copies:** a non-editable install of a first-party package in the venv, or a local namespace dir without \_\_init\_\_.py that loses to it.
7. **Landing in .pyi:** is the runtime package installed in *that* interpreter? Is it a C extension? Use `gD` for stubs, `gd` for source.
8. **Landing on base/abstract method:** expected. Use `gri` (basedpyright ≥ 1.34, ty ≥ 0.0.64, pyrefly) or `grr`/incoming calls on pyright.
9. **Nothing happens on `x.attr`:** hover `x`. If it is Unknown/Any, annotate the source of `x` (parameter, factory return, decorator with ParamSpec).
10. **Greyed-out code:** wrong `pythonVersion`/`pythonPlatform` (interpreter) or an `if not TYPE_CHECKING` branch. Fix the interpreter or `defineConstant`.

#### Config defaults for Neovim 0.11+ (proposed, untested in this research)
- Keymaps: rely on core defaults `gri` (implementation, 0.11), `grt` (type definition, 0.12), `grr` (references). Map `gd` → `vim.lsp.buf.definition()` (source-preferring) and `gD` → `vim.lsp.buf.declaration()` (stub-preferring). Add `vim.lsp.buf.typehierarchy("subtypes")` only for ty/pyrefly, and `vim.lsp.buf.incoming_calls()` for all.
- Server choice for navigation: basedpyright when you want pyright semantics plus `textDocument/implementation`. Plain pyright lacks implementation and type hierarchy. ty (beta) and pyrefly cover implementation, type hierarchy and call hierarchy.
- root_markers for monorepos: put a workspace-level marker before per-member ones, for example `{ 'pyrightconfig.json', 'uv.lock', { 'pyproject.toml', 'setup.py', 'setup.cfg', 'requirements.txt', 'Pipfile' }, '.git' }`.
- Interpreter: for pyright, add a `before_init` that walks up from `root_dir` to the first .venv/bin/python and sets `settings.python.pythonPath` (basedpyright does the root-level check itself; ty uses `VIRTUAL_ENV` then .venv). This composes with any existing `before_init` (call both).
- Settings: `python.analysis.autoSearchPaths = true`, `useLibraryCodeForTypes = true` (pyright; leave unset on basedpyright), `diagnosticMode = "openFilesOnly"`. Keep project specifics (`executionEnvironments`, `extraPaths` globs, `stubPath`) in the project's pyrightconfig.json or `[tool.pyright]`/`[tool.basedpyright]`, not in the editor.
- Project side: prefer `uv_build`/hatchling path .pth editables. With setuptools flat layout, add `[tool.uv] config-settings = { editable_mode = "compat" }` (or `config-settings-package` per member). Add `@override` and annotate public functions and factory returns. Use ParamSpec for decorators.

### Gaps
- No quantitative study found that correlates annotation coverage (or `--verifytypes` score) with go-to-definition/implementation success rates.
- No ty "infer/apply annotations" feature found in ty docs or changelog. I could not confirm whether ty inlay hints are insertable (double-click) the way basedpyright's are.
- Pyrefly `infer` flag names and its parameter-inference method (call-site or not) are not documented on the page reviewed.
