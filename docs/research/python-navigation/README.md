# Teach Neovim to find Python implementations

> Research from October 2026 into how popular editors handle Python navigation, and the design it recommended for this config. It describes the config as it was before that design shipped, with pyright as the type server. For how the config works now, see [python-navigation.md](../../python-navigation.md), which wins wherever the two disagree. The [notes](#notes) it draws on are listed at the end.

When you call a method through a base class, ABC or Protocol, your `gd` lands on the abstract method. That is what go-to-definition means in every editor. The problem is that pyright, your only type-aware server, gives you no second command to get from there to the concrete override. It does not implement `textDocument/implementation`, so `gri` fails, and references on the base method leave the overrides out. The "sometimes" comes from the environment, not from the code. Pyright takes its interpreter from whatever `python3` is on Neovim's PATH. It roots itself at the nearest `pyproject.toml`. It cannot see editable installs that use import hooks. It never hears about changes made outside the editor, because this config turns file watching off. So the same jump can land somewhere different depending on how and where Neovim was started. The editors known for accurate Python navigation fix these two halves separately. PyCharm, VS Code with Pylance, and Zed (whose default server is basedpyright) all make "implementations" a command of its own. PyCharm, VS Code, Zed and Sublime Text all work hard to pick the right interpreter and project root. For this config, the recommended design is to replace pyright with **basedpyright 1.40.2**. It runs the pyright engine (a newer version than the pinned 1.1.409) and adds go-to-implementation that understands Protocols, semantic tokens, inlay hints and `.venv` detection. Around it, feed the server the interpreter that the config's docs features already resolve, root it at the workspace rather than the nearest package, bind declaration and call hierarchy to keys, and keep exactly one type-aware server attached. Astral's ty is the server to watch: it covers more of the LSP and is far faster, but it is still in beta and does not find classes that implement a Protocol without inheriting from it.

## Go-to-definition stops at the declared type, by design

Go-to-definition is static. The server looks up the member on the declared or inferred type of the receiver. If you have `def run(r: Repo): r.save(1)` and `Repo` is an ABC, the correct LSP answer for `save` is `Repo.save`, not the subclass you meant. A headless probe during this research reproduced exactly that against the pinned pyright 1.1.409. `gd` on `r.save` returned the abstract `Repo.save`. References with the declaration included returned only the call site and the abstract method, not the `SqlRepo.save` override. A raw `textDocument/implementation` request came back with error `-32601 "Unhandled method"`. That matches pyright's source. The capabilities it announces at startup include definition, declaration, type definition, references and call hierarchy, but **no `implementationProvider` and no `typeHierarchyProvider`** ([pyright languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)). Neovim users have hit this since 2021 ([Neovim Discourse](https://neovim.discourse.group/t/pyright-go-to-implementation-not-working/1336)). In this config, `gri` is routed through the tagstack writer to `vim.lsp.buf.implementation()` ([lsp.lua](../../../lua/plugins/lsp.lua)), so in Python buffers it does nothing except warn.

No editor makes go-to-definition land on the concrete override through an abstract-typed receiver. What they all do is give "implementations" its own command. In VS Code, Go to Implementation lists "concrete implementations for an abstract method" ([VS Code code navigation](https://code.visualstudio.com/docs/editing/editingevolved)). Pylance added it to Python in a December 2024 prerelease and made it follow subtypes transitively in January 2025 ([Pylance changelog](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md); [VS Code Python, Feb 2025](https://devblogs.microsoft.com/python/python-in-visual-studio-code-february-2025-release/)). PyCharm splits the same relation into three keys: Ctrl+B for the declaration, Ctrl+Alt+B for implementations and Ctrl+U for the super method ([PyCharm navigation](https://www.jetbrains.com/help/pycharm/navigating-to-super-method-or-implementation.html)). Your complaint is therefore less about a wrong answer than about a missing command. The fix is a server that answers `textDocument/implementation`.

A second group of misses lives in the code itself, and no server fixes it. If the receiver's type is Unknown (an unannotated parameter, an untyped factory return, an untyped container element), there is no class to look the member up on, and `gd` on `obj.method()` does nothing. Pyright infers some of these, but unannotated parameters stay Unknown unless a same-named base-class method or a default value supplies a type ([pyright type inference](https://github.com/microsoft/pyright/blob/main/docs/type-inference.md)). Decorators are the other trap. Pyright treats a fully unannotated decorator as identity, but a partly annotated one such as `(f: Callable) -> Callable` erases the signature ([pyright decorators.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/analyzer/decorators.ts)). And `functools.wraps` gives the decorated object the wrapper's signature ([typeshed functools.pyi](https://github.com/python/typeshed/blob/main/stdlib/functools.pyi)). Re-exports are mostly fine. Pyright follows import aliases through `__init__.py` to the original declaration ([pyright definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)). A plain assignment like `Foo = _impl.Foo` is a variable declaration, though, so `gd` stops at the assignment. Lazy `__getattr__` packages are opaque unless a `.pyi` lists their names ([Scientific Python SPEC 1](https://scientific-python.org/specs/spec-0001/)).

## Launch context decides which code pyright analyses

A miss in the code repeats every time. A miss that comes and goes points at the environment, and this config has four environmental causes. The biggest is the interpreter. Pyright picks one in this order: `venvPath` plus `venv`, then `python.pythonPath`, then "the default Python environment" on PATH ([pyright import resolution](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)). This config sets none of the first two ([pyright_rules.lua](../../../lua/config/pyright_rules.lua) only writes severity overrides). Pyright therefore uses whatever `python3` Neovim inherited. If Neovim is started from a GUI, a multiplexer pane or another project's shell, third-party imports fail to resolve or fall back to the typeshed stubs bundled with pyright. The configured Python version can also be wrong, so branches you expect show as unreachable. The config's own docs adapter warns that `python3` can be a version-manager shim that re-reads `.python-version` relative to Neovim's cwd ([adapters/python.lua](../../../lua/config/docs/adapters/python.lua)). That same file already holds a careful `.venv` → `$VIRTUAL_ENV` → `.python-version` ladder for finding the interpreter. Today only `K`/`gK` use it, not the language server.

The other three causes stack on top of that. **Roots**: nvim-lspconfig's pyright `root_markers` is a flat list in which `pyproject.toml` comes before `.git` ([lsp/pyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyright.lua)). In Neovim 0.12, list order is priority and the search "stops at the first directory containing that marker" ([Neovim lsp.txt](https://github.com/neovim/neovim/blob/v0.12.5/runtime/doc/lsp.txt)). In a multi-package repo that means one pyright per member package, each with only its own workspace for references. If a sibling package is installed into the venv (non-editable), `gd` into it opens the site-packages copy. **Editable installs**: setuptools uses import hooks by default, and "resolving module locations using an import hook requires executing Python code", so static servers cannot follow them. `uv_build`, hatchling and PDM write path-based `.pth` files and are fine ([pyright import resolution](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)). **Staleness**: `workspace/didChangeWatchedFiles` is disabled for every server to keep the UI thread quiet ([lsp.lua](../../../lua/plugins/lsp.lua)). After a branch switch, `git pull`, codegen or `uv sync`, pyright can point at old locations until `<leader>lr`.

Landing in a `.pyi` is a symptom of the interpreter problem, not a setting you're missing. Neovim advertises `textDocument.declaration`, so pyright filters definition results to source and declaration results to stubs, "unless filtering would produce an empty list" ([pyright definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)). A stub landing means no source could be found: a C extension, a stub-only package, or a package missing from the interpreter pyright is using. Pylance users hit the same thing and got only a notification in 2026 ([pylance-release#5007](https://github.com/microsoft/pylance-release/issues/5007)). One more trap comes with any server change. Since 0.11, Neovim merges definition, implementation and reference results from every attached client ([Neovim news-0.11](https://github.com/neovim/neovim/blob/v0.12.5/runtime/doc/news-0.11.txt)), and mason-lspconfig's default `automatic_enable` already attaches ruff and dprint to Python buffers ([python-diagnostics.md](../../python-diagnostics.md)). If basedpyright is installed while pyright is still installed, both attach, and every `gd` opens a two-entry list instead of jumping.

| Symptom | Mechanism | Fix |
|---|---|---|
| `gd` on `repo.save()` lands on the abstract method | Static receiver type; pyright has no implementation request | `gri` on basedpyright; `grr` or incoming calls on the base method |
| `gri` warns "method not supported" | pyright announces no `implementationProvider` | Switch server |
| Same jump works in one session, hits a `.pyi` or nothing in another | Interpreter taken from Neovim's PATH | Set `python.pythonPath` per root from the existing ladder |
| `gd` opens site-packages copy of your own sibling package | Root per member `pyproject.toml`, non-editable or import-hook install | Workspace-level root, path-based editable install, `extraPaths` |
| `gd` points at a moved line after a branch switch or `uv sync` | File watching off | Targeted client restart |
| `gd` on `obj.method()` does nothing | Receiver is Unknown | Annotate the parameter or factory; `ParamSpec` decorators |
| `gd` stops at `Foo = _impl.Foo` | Assignment alias is a variable | `from ._impl import Foo as Foo` |
| `gd` opens a list with the same place twice | Two navigation servers attached; Neovim merges | Exactly one type-aware server |

## Accurate editors pair an implementation command with a project model

PyCharm is the reference point for "always finds the right implementation", and the reason is architectural. IntelliJ builds stub indexes ahead of time, covering the whole project and the interpreter's libraries ([IntelliJ indexing](https://plugins.jetbrains.com/docs/intellij/indexing-and-psi-stubs.html)). "Who subclasses this" is then a lookup, which is what makes the overriding/overridden gutter icons and the Inheritors and Usages hints cheap enough to show everywhere ([PyCharm inlay hints](https://www.jetbrains.com/help/pycharm/2026.2/inlay-hints.html)). Type hierarchy (Ctrl+H) and call hierarchy (Ctrl+Alt+H) open as pinnable trees with Project/Test/Library scopes ([PyCharm hierarchy](https://www.jetbrains.com/help/pycharm/viewing-structure-and-hierarchy-of-the-source-code.html)). The other half is an explicit project model. A project interpreter plus directories marked as Sources roots, which PyCharm "uses as the starting point for resolving imports" ([PyCharm content roots](https://www.jetbrains.com/help/pycharm/content-root.html)). Notably, JetBrains now lets Pyrefly replace its built-in type engine over LSP (2026.1.2 and later; local interpreters only), and pitches it as the speed fix for large codebases ([PyCharm type engine](https://www.jetbrains.com/help/pycharm/python-type-engine.html)).

VS Code with Pylance offers the full set of commands: implementation, type hierarchy since December 2023 ([VS Code Python, Dec 2023](https://devblogs.microsoft.com/python/python-in-visual-studio-code-december-2023-release/)), call hierarchy, semantic tokens and inlay hints. Its accuracy comes mostly from environment work. The Python Environments extension auto-selects a workspace `.venv` first, and "activating the venv in a terminal does not affect the editor" ([Pylance environments how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/python-environments.md); [VS Code environments](https://code.visualstudio.com/docs/python/environments)). On Python 3.13+, Pylance even runs import-hook `.pth` files in a sandbox to find editable sources ([Pylance FAQ](https://github.com/microsoft/pylance-release/blob/main/FAQ.md)). Pylance's own monorepo guide says go to definition and references do not depend on its index; the index feeds auto-import and workspace symbols ([Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md)). Lacking an index is not what costs a Neovim setup accuracy. Pylance is licensed only for Microsoft's VS Code builds, so the open alternative is basedpyright.

Zed made that alternative its default. Since v0.204 (September 2025) Python runs **basedpyright + Ruff**, chosen because basedpyright adds "inlay hints, semantic highlighting, auto-import code actions, and stricter type checking" ([zed PR #35362](https://github.com/zed-industries/zed/pull/35362)). Zed sets basedpyright to `standard` checking to match pyright ([Zed Python docs](https://zed.dev/docs/languages/python)). Its accuracy work is a toolchain selector, built on the same environment scanner as VS Code. It picks the interpreter per subproject, pushes it to the server as `python.pythonPath`, and "runs a separate server for each toolchain" ([Zed blog](https://zed.dev/blog/making-python-in-zed-fun); [Zed toolchains](https://zed.dev/docs/toolchains)). Its subproject rule is concrete enough to copy: the **outermost `pyproject.toml` that also has a workspace lockfile** (uv, poetry, pdm or Pipfile lock), falling back to the innermost `pyproject.toml` ([Zed python.rs](https://github.com/zed-industries/zed/blob/main/crates/languages/src/python.rs)). Sublime's LSP-pyright and LSP-basedpyright go further on visibility. They try an ordered list of venv strategies, and the status bar shows which finder matched ([LSP-pyright settings](https://github.com/sublimelsp/LSP-pyright/blob/master/LSP-pyright.sublime-settings)). Helix leaves venvs to the servers and merges goto results from several servers by default ([Helix changelog](https://github.com/helix-editor/helix/blob/master/CHANGELOG.md)). Its monorepo issue, where ty failed after Helix moved the working directory to the repo top, shows what happens when the root goes wrong ([helix#14641](https://github.com/helix-editor/helix/issues/14641)).

| Editor (Oct 2026) | Default Python engine | Implementations | Type hierarchy | Call hierarchy | Interpreter handling |
|---|---|---|---|---|---|
| PyCharm 2026.2 | Own index + type engine (Pyrefly optional) | Ctrl+Alt+B, gutter icons | Tree | Tree | Project interpreter + source roots |
| VS Code + Pylance 2026.4 | Pylance | Yes (transitive) | Yes | Yes | Python Environments, `.venv` first |
| Zed 1.24 | basedpyright + Ruff | Yes | Not found | Picker (Sep 2026) | Per-subproject toolchain → `pythonPath` |
| Sublime + LSP | User's pick | Yes (server-dependent) | Tree | Tree | Ordered venv strategies, status bar |
| Helix 25.07.1 | ty, ruff, jedi, pylsp (merged) | Server-dependent | No | No (PR open) | None; servers discover |
| LazyVim 16 | pyright, one-line switch to basedpyright | `gI` (empty on pyright) | Not found | `gai`/`gao` (snacks) | venv-selector.nvim |
| This config | pyright 1.1.409 + ruff + dprint | `gri` errors | No | Supported, unbound | `python3` on PATH |

The Neovim distributions follow the same pattern. LazyVim defaults to pyright behind `vim.g.lazyvim_python_lsp`, which switches to basedpyright. It turns off ruff's hover and adds venv-selector ([LazyVim python extra](https://github.com/LazyVim/LazyVim/blob/main/lua/lazyvim/plugins/extras/lang/python.lua)). Its snacks picker extra binds incoming and outgoing calls to `gai`/`gao` ([snacks_picker.lua](https://github.com/LazyVim/LazyVim/blob/main/lua/lazyvim/plugins/extras/editor/snacks_picker.lua)). AstroCommunity's Python pack defaults to basedpyright and sets `pythonPath` in `before_init` ([astrocommunity python pack](https://github.com/AstroNvim/astrocommunity/blob/main/lua/astrocommunity/pack/python/init.lua)). Two lessons come out of this survey. First, every open-source editor that ships Python reading aids ships basedpyright, ty or Pyrefly, not plain pyright. Second, the editors use tree-sitter for structure (Zed's outline and breadcrumbs default to it) and the LSP for relationships. Inlay hints and semantic tokens are off by default in Zed and Sublime ([Zed default settings](https://github.com/zed-industries/zed/blob/main/assets/settings/default.json); [Sublime LSP features](https://lsp.sublimetext.io/features/)). That fits this config's "quiet UI" stance.

## basedpyright wins on accuracy today; ty wins on speed and breadth

Every server's capabilities were read from its source in October 2026. Only three of them answer the question you actually asked.

| | pyright 1.1.414 | basedpyright 1.40.2 | ty 0.0.90 | Pyrefly 1.4.0 |
|---|---|---|---|---|
| Status | Stable | Stable fork of pyright | Beta, 0.0.x | Stable 1.x since May 2026 |
| Go to implementation | No | Yes, includes structural Protocol implementers | Yes (Jul 2026), inheritance only | Yes, inheritance only |
| Type / call hierarchy | No / yes | No / yes | Yes / yes | Yes / yes |
| Semantic tokens, inlay hints | No | Yes | Yes | Yes |
| Interpreter discovery | `python` on PATH | `./.venv` at root, then PATH | `VIRTUAL_ENV`, then `.venv` | Active venv, then `.venv` upward |
| Unannotated returns | Inferred, call-site inference | Same as pyright | Unknown unless opted in | Inferred by default |

basedpyright shipped `textDocument/implementation` in v1.34.0 (November 2025). It finds "all overrides" of a method, all subclasses when used on a class, and it "works with Protocols" ([basedpyright PR #1636](https://github.com/DetachHead/basedpyright/pull/1636)). Its test suite covers the Protocol case: a class that structurally satisfies `SupportsFoo` is returned, and one with an incompatible signature is excluded ([protocol test](https://github.com/DetachHead/basedpyright/blob/main/packages/pyright-internal/src/tests/fourslash/findAllImplementations.protocol.fourslash.ts)). ty's own tracker cites basedpyright as the reference behaviour. It says ty "currently follows nominal inheritance only", and that Pyrefly's search likewise finds only explicit subclasses ([ty#4142](https://github.com/astral-sh/ty/issues/4142)). basedpyright also auto-uses `./.venv` ([basedpyright defaults](https://docs.basedpyright.com/latest/benefits-over-pyright/better-defaults/)) and re-implements Pylance's semantic highlighting and inlay hints ([basedpyright Pylance features](https://docs.basedpyright.com/latest/benefits-over-pyright/pylance-features/)). Because it is pyright underneath, your `pyrightconfig.json` files, the definition-to-source and declaration-to-stub split, and the import-resolution rules all carry over unchanged. Two caveats are documented. First, its implementation search scans the whole project, and the author calls it "kind of slow" on big projects. Second, references on an override are stricter than Pylance's: `grr` on `SqlRepo.save` does not list calls made through `Repo` ([basedpyright#1447](https://github.com/DetachHead/basedpyright/issues/1447)). To find callers of an interface method, run `grr` on the base method.

ty is the strongest alternative. It has the widest LSP coverage of any Python server (type hierarchy, folding, selection range), finds uv workspace roots on its own, and has the best published edit latency. On a "load-bearing file" in PyTorch it recomputed diagnostics in 4.7 ms against pyright's 386 ms, though that is Astral's own benchmark ([Astral ty blog](https://astral.sh/blog/ty); [ty LSP docs](https://docs.astral.sh/ty/features/language-server/)). It loses here for three reasons. It is still a beta that ships several releases a week. Its implementation search misses classes that satisfy a Protocol without inheriting from it. And by default it leaves unannotated return values as Unknown: return-type inference only arrived on 2026-10-16, as an opt-in setting ([ty changelog](https://github.com/astral-sh/ty/blob/main/CHANGELOG.md)). For an incompletely annotated codebase, that last point directly cuts the number of `obj.method()` jumps that resolve. Pyrefly is stable, infers aggressively, has built-in Django and Pydantic support, and is the engine JetBrains and Positron adopted ([PyCharm type engine](https://www.jetbrains.com/help/pycharm/python-type-engine.html); [Posit evaluation](https://opensource.posit.co/blog/2026-03-31_python-type-checkers/)). But it indexes at most 2000 workspace files by default, and references, rename and hierarchies depend on that index ([pyrefly lsp.rs](https://github.com/facebook/pyrefly/blob/main/pyrefly/lib/commands/lsp.rs)). Its docs also say it works in Neovim only if the venv was activated before Neovim started ([Pyrefly IDE docs](https://pyrefly.org/en/docs/IDE/)). Speed is a real argument against the pyright family: Pyrefly's vendor benchmark had pyright using over 3 GB on numpy against Pyrefly's 1 GB ([Pyrefly benchmark](https://pyrefly.org/blog/speed-and-memory-comparison/)). Neither vendor measured navigation accuracy, though, and accuracy is what this complaint is about.

## Seven changes make this config implementation-aware

### Swap the server, keep the machinery

Replace `pyright` with `basedpyright` in the `servers` table in [lsp.lua](../../../lua/plugins/lsp.lua). Pin `"basedpyright": "1.40.2"` in [mason-tool-versions.lock](../../../mason-tool-versions.lock), remove the pyright pin, and uninstall pyright. Otherwise mason-lspconfig's `automatic_enable` re-attaches it and every jump turns into a duplicate list. A cleaner option is to set `automatic_enable = false` and declare ruff (and dprint, if other filetypes depend on it) explicitly, so the set of attached servers is visible in one table. In `LspAttach`, turn off ruff's `hoverProvider`, as Ruff's own Neovim guide does ([Ruff editor setup](https://docs.astral.sh/ruff/editors/setup/)). Put `typeCheckingMode = "standard"` under `settings.basedpyright.analysis`, as Zed does. Without it, basedpyright's default `recommended` mode floods a Pydantic-heavy project with new warnings, which is the noise [python-diagnostics.md](../../python-diagnostics.md) was built to tame. The per-project severity machinery mostly carries over. In [pyright_rules.lua](../../../lua/config/pyright_rules.lua), generalise the `name = "pyright"` client lookups. Write the overrides to `settings.basedpyright.analysis.diagnosticSeverityOverrides`; the settings doc calls the editor-side copy "discouraged" but still supports it ([basedpyright LS settings](https://docs.basedpyright.com/latest/configuration/language-server-settings/)). The picker can then offer the `hint` severity it currently hides because pyright discards it. Also update `M.server` in [brief/python.lua](../../../lua/config/docs/brief/python.lua) and the provider key in [hover.lua](../../../lua/config/docs/hover.lua). Keep the server name in one variable, the way LazyVim does, so trying ty later is a one-line change. Zed's code notes that basedpyright changed how it reads flat versus nested `analysis` sections in v1.39.10 ([Zed python.rs](https://github.com/zed-industries/zed/blob/main/crates/languages/src/python.rs)). Assert that the settings actually reach the server in the existing real-server test lane ([pyright_rules_spec.lua](../../../tests/spec/e2e-lsp/pyright_rules_spec.lua)).

### Give the server the project's interpreter

Turn the docs adapter's `venv_dir`/`interpreter` ladder into a shared module. Call it from the same `before_init` that injects severities, and have it set `settings.python.pythonPath`; basedpyright still reads that one `python.*` key. Leave the key unset when the ladder finds nothing, so basedpyright's own `./.venv` check can run. One change to the ladder matters. Today `venv_dir` looks only in the root itself and ignores a `$VIRTUAL_ENV` outside the root. A uv workspace keeps one `.venv` at the workspace top, and members install each other editable ([uv workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/)). So a member-rooted client finds nothing. Walk upward to the workspace or git root before falling back. Then copy Sublime's best idea: show the interpreter the Python client started with in [statusline.lua](../../../lua/config/statusline.lua), or on a `:PythonEnv` command. A wrong interpreter becomes something you can see instead of a mysterious jump. venv-selector.nvim is the off-the-shelf version (Neovim 0.11+, injects `pythonPath`, needs `fd`), but the hand-rolled ladder already exists and fits the repo's style ([venv-selector](https://github.com/linux-cultist/venv-selector.nvim)).

### Root at the workspace, not the member

Give basedpyright a `root_dir` function that applies Zed's rule. A `pyrightconfig.json` wins. Otherwise take the outermost `pyproject.toml` that has a uv, poetry, pdm or Pipfile lockfile next to it, else the innermost `pyproject.toml`, bounded by the git root the way [lsp_root.lua](../../../lua/config/lsp_root.lua) already bounds ts_ls. Neovim 0.12's nested-list `root_markers` does not solve this, because the nearest `pyproject.toml` still wins. One workspace-level client sees every member for references and implementations. Cross-member imports then resolve through the workspace's own config: `executionEnvironments`, or `extraPaths` globs such as `packages/*/src`. Globs need pyright 1.1.414 or basedpyright 1.40.1, which the current 1.1.409 pin lacks ([pyright import resolution](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)). Stored severity rules are keyed by realpath'd root, so changing the root strategy orphans rules recorded under member roots, and the picker needs a one-time migration or a note. Some fixes belong to the project, not the editor. Prefer `uv_build` or hatchling editables; for setuptools flat layouts, set `[tool.uv] config-settings = { editable_mode = "compat" }` ([pyright import resolution](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)). Annotate factory returns, type decorators with `ParamSpec` ([PEP 612](https://peps.python.org/pep-0612/)), and re-export names with `as` rather than by assignment.

### Bind the missing commands

With basedpyright attached, the existing `gri` starts working with no new code. On a method it lists overrides; on a class name it lists subclasses, which covers most of what type hierarchy would give. Add a `declaration` command to [tagstack.lua](../../../lua/config/tagstack.lua) and map `gD` to it in Python buffers. That makes the stub-preferring jump deliberate, and it fixes the [keybindings.md](../../keybindings.md) row that wrongly calls `gD` an LSP default. Call hierarchy already works on pyright and basedpyright but has no key. Bind Telescope's `lsp_incoming_calls` and `lsp_outgoing_calls` ([telescope.txt](https://github.com/nvim-telescope/telescope.nvim/blob/master/doc/telescope.txt)) to `grc` (callers) and `grC` (callees). Neither key is taken, and both stay inside the `gr` group that which-key already labels. Reading an interface then becomes three keys: `gd` to the abstract method, `gri` to the concrete overrides, `grc` to the callers. Type hierarchy (`vim.lsp.buf.typehierarchy`) only becomes worth binding if you move to ty or Pyrefly.

### Let semantic tokens reach Python

basedpyright emits `selfParameter`, `clsParameter`, `decorator`, `parameter`, `readonly` and `defaultLibrary` tokens ([basedpyright semanticTokensProvider.ts](https://github.com/DetachHead/basedpyright/blob/main/packages/pyright-internal/src/languageService/semanticTokensProvider.ts)). Neovim applies them over tree-sitter automatically. [syntax_emphasis.lua](../../../lua/config/syntax_emphasis.lua) was written around gopls tokens, so give it Python links. Remember the repo's own finding that semantic tokens outrank tree-sitter captures, which means a declaration-bolding tweak has to be wired at both levels ([memory](../../memory/nvim-lsp-semantic-tokens-outrank-treesitter.md)). Add Python docstrings (`@string.documentation`) to the comment-dimming tier; right now they stay at full string colour. basedpyright turns every inlay-hint kind on by default ([basedpyright LS settings](https://docs.basedpyright.com/latest/configuration/language-server-settings/)). Neovim keeps them off until toggled, and the existing capability-gated `<leader>uh` appears on its own. Set `variableTypes` and `genericTypes` to false so a toggle shows return types and argument names, not clutter. An outline sidebar is optional. aerial.nvim (v4.0.0, Neovim 0.11+, tree-sitter first) is the best-maintained choice ([aerial.nvim](https://github.com/stevearc/aerial.nvim)), behind a toggle. PyCharm-style override gutter icons have no Python plugin. They could be built later from `documentSymbol` plus `textDocument/implementation`, at the cost of one request per symbol.

### Refresh after the world changes

Keep file watching off; the reason it was turned off still holds. Add a targeted restart instead. When focus comes back, compare `.git/HEAD` and the venv's `site-packages` mtime with the values recorded when the Python client started. If either changed, run `:lsp restart` on that client (new in 0.12; [Neovim news](https://github.com/neovim/neovim/blob/v0.12.5/runtime/doc/news.txt)). The docs adapter already invalidates its interpreter cache on mtime for the same reason, so the approach has precedent in the repo. This is a design proposal and has not been tested.

### Prove it, then document it

Add a real-server spec next to the existing ones, for example tests/spec/e2e-lsp/python_navigation_spec.lua. Use the probe's three-file fixture (ABC base, concrete override, call through the base type) plus a Protocol-only implementer. Assert that `gd` lands on the abstract method, that implementation returns both concrete classes, and that exactly one Python navigation client is attached. Two repo memories apply. This test lane self-skips unless mason's bin directory is on PATH ([memory](../../memory/nvim-test-lsp-needs-mason-path.md)), and buffers in LSP filetypes should be loaded with `bufadd`/`bufload` rather than `:edit` ([memory](../../memory/nvim-e2e-no-edit-lsp-filetypes.md)). Once it ships, update [python-diagnostics.md](../../python-diagnostics.md) for the new namespace, and fix the `gD`, `grr` and server-list rows in [keybindings.md](../../keybindings.md). Also record why basedpyright was chosen; no doc in the repo explains the current choice of pyright.

## Conclusion

The fact that the failure is intermittent is the most useful diagnostic you have. A dispatch miss happens on every attempt at the same call. A miss that varies between sessions or packages almost always means the server analysed a different project than the one on screen: another interpreter, another root, another copy of the package. The best editors treat that as a product problem. They show the interpreter and the subproject, while Neovim leaves both invisible. The cheapest high-value change here may be the statusline readout, because it turns a puzzling bug into a fact you can see before you ever press `gd`.

The gap to PyCharm is also narrower than its reputation suggests. What its index really buys is cheap answers to "who overrides this", and basedpyright's on-demand `gri` now gives the same answers, only more slowly. What is still missing outside JetBrains is the always-on version of that answer: override markers in the gutter. This research found no Neovim plugin that draws them for Python, and building one is now a client-side job rather than a server limit. Server choice for Python is now a moving target. ty gained go-to-implementation in July 2026 and inference for unannotated code in October. So key the config's Python machinery on a role ("the Python type server") rather than the literal name `pyright`, and revisit the choice in a few months instead of locking it in.
