# VS Code + Pylance vs pyright vs basedpyright: Python navigation, readability and LSP accuracy (state as of October 2026)

> A research note from October 2026, one of the sources for [the Python navigation research](README.md). It describes other editors and tools as of that date, and this config as it was before the switch to basedpyright.

Versions referenced (as of 2026-10-21): Pylance stable **2026.4.1** (23 Sep 2026), prerelease **2026.4.101** (15 Oct 2026) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md); pyright **1.1.414** (9 Sep 2026) — [pyright releases](https://github.com/microsoft/pyright/releases); basedpyright **v1.40.2** (4 Oct 2026) — [basedpyright releases](https://github.com/DetachHead/basedpyright/releases). Pylance README/FAQ/TROUBLESHOOTING all say "Last content update aligned with Pylance 2026.4.1" — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md). The VS Code Python docs pages used here carry `DateApproved: 02/04/2026`, so they are ~8 months older than the Pylance repo docs — [VS Code Python editing docs](https://code.visualstudio.com/docs/python/editing).

## Navigation: Definition / Declaration / Type Definition / Implementation / References / Call Hierarchy / Type Hierarchy

### Takeaway
Open-source pyright already implements definition, declaration (stub-preferring), type definition, references, document/workspace symbols, rename and call hierarchy over LSP. It does **not** implement `textDocument/implementation`, type hierarchy, semantic tokens, inlay hints, folding or selection ranges. basedpyright adds `textDocument/implementation` (v1.34.0, Nov 2025) but still has no type hierarchy. Pylance has all of these, plus pytest-fixture, string-literal-module and inlay-hint go-to-def. "Go to Source Definition" (the TypeScript command) does not exist for Python. The stub-vs-source split is done instead by Definition (prefers `.py`) vs Declaration (prefers `.pyi`).

### Cited Findings
**Capability matrix from source code (primary evidence)**
- pyright's `languageServerBase.ts` registers handlers and advertises `definitionProvider`, `declarationProvider`, `typeDefinitionProvider`, `referencesProvider`, `documentSymbolProvider`, `workspaceSymbolProvider`, `hoverProvider`, `documentHighlightProvider`, `renameProvider` (with prepare), `completionProvider`, `signatureHelpProvider`, `codeActionProvider`, `executeCommandProvider` and `callHierarchyProvider: true`. It has no `implementationProvider`, `typeHierarchyProvider`, `semanticTokensProvider`, `inlayHintProvider`, `foldingRangeProvider`, `selectionRangeProvider` or `codeLensProvider` — [pyright languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- basedpyright's `languageServerBase.ts` advertises everything pyright does plus `implementationProvider`, `inlayHintProvider: true`, `semanticTokensProvider` (full, no delta/range), `documentOnTypeFormattingProvider` (trigger `{`, used for f-string auto-insert), and `workspace.fileOperations.willRename` (for module/package rename). It has no `typeHierarchyProvider`, `foldingRangeProvider` or `codeLensProvider` — [basedpyright languageServerBase.ts](https://github.com/DetachHead/basedpyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- pyright's own feature list: "Find Definitions…", "Find References…", "Rename Symbol…", "Find Symbols within the current document or within the entire workspace", "View call hierarchy information — calls made within a function and places where a function is called", and an "Organize Imports command" — [pyright docs/features.md](https://github.com/microsoft/pyright/blob/main/docs/features.md)

**Go to Definition vs Go to Declaration (stubs vs source)**
- Pylance 2021.2.1 (10 Feb 2021): "Go-to-definition now brings you to source files (e.g. `.py` files), and a new 'go-to-declaration' option brings you to stub files (`.pyi`). If either would otherwise return no result, Pylance will bring you to whichever files are available." The pyright side of this landed in 2021.2.3 (17 Feb 2021): "Separated behavior of 'go to definition' and 'got to declaration'" — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- In pyright's source, `onDefinition` uses `DefinitionFilter.PreferSource` and `onDeclaration` uses `DefinitionFilter.PreferStubs`, **but only if the client advertises `textDocument.declaration` capability**. Otherwise both use `DefinitionFilter.All`, which returns stub and source locations together — [pyright languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- `filterDefinitions`: "attempt to only show only pyi files in go-to-declaration and none in go-to-definition, unless filtering would produce an empty list" — [pyright definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)
- pyright's definition provider calls `evaluator.resolveAliasDeclaration(decl, resolveLocalNames=true, {allowExternallyHiddenAccess: true})`. Import aliases, including re-exports through `__init__.py`, are therefore followed to the original declaration, not the import line. For an overloaded function it **adds every overload declaration** as a separate location. When the resolved declaration is in a stub, it uses `sourceMapper.findDeclarations` to add the matching `.py` declarations — [pyright definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts)
- Neovim's default client capabilities include `declaration = { linkSupport = true }`, `implementation = { linkSupport = true }` and `typeDefinition = { linkSupport = true }`, and the protocol module knows `textDocument/prepareTypeHierarchy`, `typeHierarchy/subtypes` and `typeHierarchy/supertypes` — [neovim runtime/lua/vim/lsp/protocol.lua](https://github.com/neovim/neovim/blob/master/runtime/lua/vim/lsp/protocol.lua)
- Pylance 2021.2.4 (24 Feb 2021): "The mapping of stub files to source files has been greatly improved. Go-to-definition and doc strings should now work for a much wider range of code." 2022.10.21: "Improved `go to definition` behavior when multiple `pyi` are used for 1 `py` file" (#3227) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Stub-only case (pylance-release #5007, opened 25 Oct 2023): when stub and source both exist, def→`.py` and decl→`.pyi`. With no stub, both go to `.py`. With a stub only (stub-only package or compiled module), both go to `.pyi`, which confuses users. Fixed in prerelease 2026.3.102 (4 Sep 2026) as "Add an informational notification when 'go to definition' falls back to 'go to declaration' behaviour" — [pylance-release#5007](https://github.com/microsoft/pylance-release/issues/5007); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- VS Code's Python editing doc describes only Go to Definition, Peek Definition, Go to Declaration and Peek Declaration under "Navigation". It does not mention implementation or hierarchies — [VS Code Python editing docs](https://code.visualstudio.com/docs/python/editing)

**Go to Type Definition**
- Pylance 2021.12.0 (2 Dec 2021): "Pylance now supports Go to Type Definition" — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md). Current pyright advertises `typeDefinitionProvider` and implements `onTypeDefinition` via `TypeDefinitionProvider`, so it is now open source and present in pyright and basedpyright — [pyright languageServerBase.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageServerBase.ts)
- VS Code generic: Go to Type Definition is `editor.action.goToTypeDefinition` with no default keybinding — [VS Code Code Navigation docs](https://code.visualstudio.com/docs/editing/editingevolved)

**Go to Implementation(s)**
- Pylance: "Enhancement: Support go-to-implementation" (#4329) in prerelease 2024.12.100 (16 Dec 2024). The maintainer said "we're still discussing how this should behave". It was followed in 2025.1.101 (22 Jan 2025) by "go to implementation should find implementation of all sub types transitively" (#6775). A later fix, "[TSP] Goto implementation doesn't work for Pyrefly" (#8127), shipped in 2026.3.101 (27 Aug 2026) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md); [pylance-release#4329](https://github.com/microsoft/pylance-release/issues/4329)
- The original request (2021 discussion #2642) was to list every override of an inherited method `f` from the base — [pylance-release#4329](https://github.com/microsoft/pylance-release/issues/4329)
- VS Code generic semantics: Go to Implementation (Ctrl/Cmd+F12) lists implementors for an interface and concrete implementations for an abstract method — [VS Code Code Navigation docs](https://code.visualstudio.com/docs/editing/editingevolved)
- basedpyright v1.34.0 (19 Nov 2025): "implement `textDocument/implementation` aka 'Go to Implementations'" (PRs #1636, #1649). It is documented as "basedpyright supports 'Go to Implementations' / 'Find All Implementations' from pylance" — [basedpyright v1.34.0 release](https://github.com/DetachHead/basedpyright/releases/tag/v1.34.0); [basedpyright Pylance features](https://docs.basedpyright.com/latest/benefits-over-pyright/pylance-features/)
- Upstream pyright has no `implementationProvider` (see capability matrix above). A 2021 Neovim user report shows "method textDocument/implementation is not supported" with pyright — [neovim discourse](https://neovim.discourse.group/t/pyright-go-to-implementation-not-working/1336)

**Find All References**
- pyright streams results ("Added streaming support for 'find all references'", 2020.10.1). Library references are not returned "unless that library source file is currently open". The search is allowed into libraries "if invoked from non-user files" (2020.7.x). Pylance 2021.12.0 improved "Performance of Find All References and Rename Symbol… for large workspaces". 2023.1.21 fixed "Find All References on any `__init__` shows every constructor for every class" (#3802). 2026.3.100 (19 Aug 2026) fixed "Find All References doesn't ignore files in `__editable__.modulename.xxx` directories" (#7412) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Overridden methods: with `F.f` abstract, `B.f` overriding, and `lst: list[F] = [B()]; [l.f() for l in lst]`, **basedpyright** Find References on `B.f` returns only `B.f` and its own usage. **Pylance** also returns `F.f` and the call through `list[F]`. The basedpyright maintainer prefers the stricter result. The issue is open, labelled "pylance parity"/"pycharm parity" — [basedpyright#1447](https://github.com/DetachHead/basedpyright/issues/1447)
- In multi-root workspaces, Find all references and Go to definition are per workspace folder. Only Workspace Symbol search aggregates across folders — [Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md)

- Pylance-level fixes and enhancements: "Call Hierarchy always returns no results for function aliased via `import as`" (2023.3.41, #3893). "Show Call Hierarchy doesn't handle overridden methods correctly" (2023.7.31, #2774). In 2026.3.100 (19 Aug 2026): "Add paths next to references when 'Show Call Hierarchy' is run" (#5104), "Filter or Visually Distinguish Workspace vs Library Symbols in Outgoing Call Hierarchy" (#7910) and "Virtual workspace has duplicates for show call hierarchy" (#5811) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)

**Type Hierarchy (supertypes/subtypes)**
- Python in VS Code December 2023 release (blog 7 Dec 2023): with Pylance, right-click → "Show Type Hierarchy" lets you "move through a symbol's subtypes and its supertypes" — [Python in VS Code Dec 2023 release](https://devblogs.microsoft.com/python/python-in-visual-studio-code-december-2023-release/)
- Pylance 2023.11.13 (15 Nov 2023): "Add support for 'Show super type Hierarchy' command" (#4978). 2024.5.102: no results for types declared in notebooks (#5832). In 2026.2.104 (2 Jun 2026): "Type hierarchy only finds direct subtypes when methods have `@override` decorator" (#6885), plus "[TSP] typeHierarchy support" (#8028) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- basedpyright: issue #355 ("show class hierarchy or method override like pycharm", opened 12 May 2024) is still **open**. The maintainer's stated direction is `textDocument/implementation` (since shipped). A May 2025 comment notes LSP 3.17 type hierarchy is supported by Neovim and VS Code. No merged type hierarchy implementation — [basedpyright#355](https://github.com/DetachHead/basedpyright/issues/355)

**Other Pylance-only go-to-definition targets**
- Overloaded operators and special methods: Pylance 2023.6.11 (7 Jun 2023) "Provides go to def support for overloaded operators and special method names" (#3759) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md). basedpyright supports go-to-def on operators and "takes it a step further by also showing hover information" (v1.33.0, 7 Nov 2025). - Module paths in strings: Pylance 2023.4.41 "Go to definition by python module path in string" (#3700). It is now controlled by `python.analysis.gotoDefinitionInStringLiteral` (boolean, **default `true`**, resource scope), which works on `include("blog.urls")`, `importlib.import_module("pkg.utils")` and `"myapp.Reporter"` in a Django `ForeignKey` (the last needs `enableDjangoSupport`) — [setting doc](https://github.com/microsoft/pylance-release/blob/main/docs/settings/python_analysis_gotoDefinitionInStringLiteral.md). basedpyright: still an open parity issue, "make strings that look like modules clickable" (#313) — [basedpyright pylance-parity issues](https://github.com/DetachHead/basedpyright/issues?q=is:issue+is:open+label:%22pylance+parity%22)
- pytest fixtures: `python.analysis.enablePytestSupport` "Enable pytest goto def and inlay hint support for fixtures" (default `true`, `false` in light mode) — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md). basedpyright: "support pytest" (#311) open — [basedpyright pylance-parity issues](https://github.com/DetachHead/basedpyright/issues?q=is:issue+is:open+label:%22pylance+parity%22)
- Inlay hint parts: Pylance 2024.8.101 "Support 'go to def' and interacting with inlay hint components" (#5210). 2024.9.100: go-to-def on inlay hints distinguishes subtypes (#6346) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md). basedpyright #651 ("go to definition" on inlay hints / `location`) is open — [basedpyright pylance-parity issues](https://github.com/DetachHead/basedpyright/issues?q=is:issue+is:open+label:%22pylance+parity%22)
- Overrides: `python.analysis.gotoOverrideCodeLens` (**Experimental**, default `false`) adds "a CodeLens on methods that override a base-class member. Clicking it peeks the overridden declaration" — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)

### Inferences
- Under Neovim, pyright and basedpyright both see `textDocument.declaration` in the client capabilities. So `vim.lsp.buf.definition()` should prefer `.py` source, and `vim.lsp.buf.declaration()` should prefer `.pyi` stubs, the same split as Pylance F12 vs "Go to Declaration". This follows from pyright's `hasGoToDeclarationCapability = !!capabilities.textDocument?.declaration` plus Neovim's advertised `declaration` capability. Not tested end to end.
- Overloads produce multiple definition locations in pyright-based servers, so Neovim will open a quickfix/location list rather than jump directly. A picker (Telescope `lsp_definitions`) handles this better.
- Navigation features available to a Neovim config by server:

| Feature | pyright (OSS) | basedpyright | Pylance (VS Code only) |
|---|---|---|---|
| definition (prefers .py) / declaration (prefers .pyi) | yes | yes | yes (since 2021.2) |
| typeDefinition | yes | yes | yes (since 2021.12) |
| implementation | no | yes (v1.34.0, Nov 2025) | yes (2024.12.100, transitive since 2025.1.101) |
| references | yes | yes (stricter on overrides) | yes (includes base-typed calls) |
| callHierarchy in/out | yes | yes | yes (+ workspace/library filtering, 2026.3.100) |
| typeHierarchy super/sub | no | no (#355 open) | yes (Dec 2023) |
| go-to-def on operators | no | yes (+hover) | yes (2023.6) |
| go-to-def in module-path strings | no | no (#313) | yes, `gotoDefinitionInStringLiteral` default true |
| pytest fixture go-to-def | no | no (#311) | yes, `enablePytestSupport` |
| override CodeLens | no | no | experimental `gotoOverrideCodeLens` |

### Gaps
- No Pylance doc describes go-to-implementation semantics for ABCs vs `Protocol`s (structural implementers), for example whether classes that only structurally satisfy a Protocol are listed. Only "all sub types transitively" (#6775) is documented. basedpyright's implementation semantics for Protocols are also undocumented beyond a screenshot.
- The exact Pylance version that first shipped subtype hierarchy could not be pinned. The changelog only records the supertypes command (2023.11.13), and the blog dates the feature to the Dec 2023 release.
- No primary maintainer statement was found on why `textDocument/implementation` and type hierarchy are kept out of upstream pyright. The absence is evidenced only by source code.

## Indexing, scale, monorepos and import resolution (Pylance settings vs pyright/basedpyright config)

### Takeaway
Pylance's indexer, with settings such as `indexing`, `userFileIndexingLimit` and `packageIndexDepths`, and its light/default/full `languageServerMode` are Pylance-only. They mainly feed auto-imports and workspace symbols, not go-to-definition or references. pyright and basedpyright have no persistent index. They resolve by import roots: `executionEnvironments`, `extraPaths` (now with glob expansion), `src` auto-search, and `.pth` editable installs. For a monorepo in Neovim, the levers are `executionEnvironments`/`extraPaths` in `pyrightconfig.json`/`[tool.pyright]`, path-based editable installs, `diagnosticMode = "openFilesOnly"`, and basedpyright's `configFilePath`.

### Cited Findings
**Pylance-only scale settings (names and defaults, Pylance 2026.4.1)**
- `python.analysis.languageServerMode`: `light` | `default` (default) | `full`. Per-mode defaults: `exclude` `["**"]`/`[]`/`[]`; `useLibraryCodeForTypes` false/true/true; `enablePytestSupport` false/true/true; `indexing` false/true/true; `userFileIndexFollowSymlinkedFolders` true/true/true; `autoImportCompletions` false/false/true; `showOnlyDirectDependenciesInAutoImport` false/false/true; `regenerateStdLibIndices` false/false/true; `userFileIndexingLimit` 2000/2000/-1; `includeAliasesFromUserFiles` false/false/true; `inlayHints.functionReturnTypes` false/false/true; `inlayHints.pytestParameters` false/false/true; `supportRestructuredText` true/true/true; `supportDocstringTemplate` false/false/false; `nodeExecutable` ""/""/"auto" — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- `python.analysis.indexing` (default `true`, `false` in light). It indexes user files and installed libraries "to improve features such as auto-import, add import, workspace symbols". "Disabling indexing doesn't impact most IntelliSense features" — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md); [indexing setting doc](https://github.com/microsoft/pylance-release/blob/main/docs/settings/python_analysis_indexing.md). Added in 2022.1.3 (21 Jan 2022) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- `python.analysis.userFileIndexingLimit`: default **2000** (-1 = all; -1 in full mode). Made configurable in 2023.5.51 (#4417). Reducing it "can reduce auto-import coverage. Workspace symbol search can still find symbols in unindexed files" — [userFileIndexingLimit doc](https://github.com/microsoft/pylance-release/blob/main/docs/settings/python_analysis_userFileIndexingLimit.md); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- `python.analysis.packageIndexDepths`: by default only top-level modules are indexed (depth 1). Default overrides: sklearn 2, matplotlib 2, scipy 2, django 4, flask 2, fastapi 2, cuda 3 (`includeAllSymbols: true`). Full mode uses `{name:"", depth:4, includeAllSymbols:true}`. `depth: 0` acts as an exclude prefix. Introduced 2022.10.21. Django default depth was raised in 2026.2.104 — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Other index settings: `persistAllIndices` (default true), `regenerateStdLibIndices` (false), `includeAliasesFromUserFiles` (false), `userFileIndexFollowSymlinkedFolders` (true; added 2026.2.100), `includeVenvInWorkspaceSymbols` (false; needs indexing), `includeExtraPathSymbolsInSymbolSearch` (false) — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- `python.analysis.diagnosticMode`: `openFilesOnly` (default) | `workspace`. `python.analysis.typeCheckingMode` in Pylance defaults to **`off`**, overridable by `pyrightconfig.json`/`pyproject.toml` — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- Exclusion: `python.analysis.exclude` (default `[]`; `["**"]` in light). "files in the exclude paths may still be included in the analysis if they are referenced (imported)". `python.analysis.useDefaultExcludes` (default `true`) adds `**/node_modules`, `**/__pycache__`, `**/__editable__.*`, hidden dirs and auto-detected venvs. `python.analysis.ignoredPackages`, `python.analysis.excludeLibraryDiagnostics` (default false) and `python.analysis.disableBundledStubs` (default false) are also available — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- Memory: VS Code's bundled Node has pointer compression (≈4 GB limit). `python.analysis.nodeExecutable` (path or `"auto"`) plus `python.analysis.nodeArguments` (default `--max-old-space-size=8192`) raise it. Recommended heaps: <5k files 8192; 5k–20k files 12288–16384; >20k files 16384–32768 — [Pylance TROUBLESHOOTING](https://github.com/microsoft/pylance-release/blob/main/TROUBLESHOOTING.md); [Pylance performance how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/performance-tuning.md)
- Performance presets: large = `{languageServerMode:"light", diagnosticMode:"openFilesOnly", indexing:false}`; medium = `{diagnosticMode:"openFilesOnly", userFileIndexingLimit:1000, indexing:true}`; small = `{languageServerMode:"full", diagnosticMode:"workspace"}` — [Pylance performance how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/performance-tuning.md)
- Each `extraPaths` directory "becomes an import search root". Broad globs (for example `**/site-packages`) can expand to hundreds of dirs. Glob expansion happens once at config load — [Pylance performance how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/performance-tuning.md)

**Monorepo/multi-root (Pylance-only experimental features)**
- Multi-root: Pylance "Creates a separate analysis service (analyzer instance) for each workspace folder", each with its own interpreter, config lookup, include/exclude/extraPaths. The memory cost is "High (one analyzer per folder)" — [Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md)
- `python.analysis.useNearestConfiguration` (**Experimental**, default false; proposal #5564 shipped in 2026-01-13 prerelease 2025.12.100) discovers `pyrightconfig.json` or `pyproject.toml` with `[tool.pyright]` in subdirectories and creates a "virtual workspace" for each. Cross-workspace imports still need `extraPaths` — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- `python.analysis.usePerProjectEnvironments` (default false) gives a separate interpreter per `python-envs.pythonProjects` entry. It replaces the deprecated `python.analysis.addFoldersForPythonProjects`. `python.analysis.addExtraPathsForPythonProjects` (**Experimental**, default false) auto-adds each project's source root (`src` if present, etc.) to `extraPaths`. It follows uv `[tool.uv.sources]` path entries, Poetry path/develop deps, and PDM/Rye/PEP 508/PEP 735 `file:` refs transitively — [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- Conflict: VS Code's environments doc (approved 02/04/2026) says "Pylance does not support multiple Python projects with different interpreters in the same workspace… uses a single interpreter for the entire workspace". The newer Pylance README (2026.4.1) documents `usePerProjectEnvironments` for exactly that — [VS Code Python environments docs](https://code.visualstudio.com/docs/python/environments); [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md)
- Settings precedence: pyright defaults → `pyrightconfig.json`/`[tool.pyright]` → VS Code user → workspace/folder → `languageServerMode` overrides. If `pyrightconfig.json` exists, its include/exclude win over `python.analysis.include/exclude`. `extraPaths` from project config and VS Code settings are **not merged**: the project config list wins — [Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md)

**pyright/basedpyright import resolution (applies in Neovim)**
- Resolution order for absolute imports: (1) `stubPath` (default `./typings`); (2) workspace code — execution-environment root, then that env's `extraPaths` (or `python.analysis.extraPaths`), then local `src` if no execution environment; (3) installed packages (`-stubs` package → inline `.pyi` → `py.typed` → library `.py` if `useLibraryCodeForTypes`); (4) typeshed stdlib; (5) typeshed third-party; (6) the importing file's directory and parent directories within the workspace — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)
- `extraPaths` entries (config, execution env, or setting) may contain `*`, `**`, `?` globs. They expand to directories only, sorted deterministically. Literal entries win on duplicates, and symlinks are not resolved — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)
- `executionEnvironments` entries: `root` (required), `extraPaths` (overrides, not merges, the default extraPaths), `pythonVersion`, `pythonPlatform`, and per-env diagnostic rules. A file is assigned to the **first** matching root. "if file A … imports a second file B within a second execution environment, any imports from B will use the extraPaths in the second execution environment" — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md); [Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md)
- pyright `exclude` defaults per current docs: `**/node_modules`, `**/__pycache__`, `**/.*`, `**/__editable__.*` and auto-detected venv directories. "Any paths you specify here are added on top of these defaults rather than replacing them." Excluded files may still be analyzed if imported — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)
- `python.analysis.autoSearchPaths` "automatically adds common search paths like 'src' if there are no execution environments defined" — [pyright settings.md](https://github.com/microsoft/pyright/blob/main/docs/settings.md)
- Editable installs: import-hook-style `.pth` files are "not usable by Pyright", so use path-based `.pth`. setuptools uses hooks by default, so use compat or strict mode. With uv + setuptools: `[tool.uv] config-settings = { editable_mode = "compat" }`. The "`uv_build` backend always uses path-based `.pth` files". Hatchling and PDM are path-based by default — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)
- Pylance-only: on Python 3.13+, `python.analysis.enableEditableInstalls` (default `true` per FAQ/TROUBLESHOOTING) executes import-hook `.pth` files in a sandbox to find sources — [Pylance FAQ](https://github.com/microsoft/pylance-release/blob/main/FAQ.md); [Pylance TROUBLESHOOTING](https://github.com/microsoft/pylance-release/blob/main/TROUBLESHOOTING.md). Related fixes: uv editable packages not resolved (2025.12.100, #7650), "PEP 829 needs to be handled for editable install paths" (2026.3.100), and `enableEditableInstalls` breaking relative imports (2026.3.102) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Namespace packages: Pylance 2025.10.2 fixed a regression where it "no longer detects workspace or PEP 420 namespace packages". 2025.12.100 added "Automatically figure out index depth for namespace package" — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- basedpyright-only monorepo settings: `basedpyright.analysis.configFilePath` (directory or file of `pyrightconfig.json`/`pyproject.toml`, e.g. `vim.fn.getcwd() .. "/backend"`) and `basedpyright.analysis.fileEnumerationTimeout` (seconds before a "slow enumeration" warning, default 10) — [basedpyright LS settings](https://docs.basedpyright.com/latest/configuration/language-server-settings/)

### Inferences
- What Pylance's index buys for *reading* code is mostly faster, wider workspace-symbol search and auto-import coverage. Go to definition, references, rename and hover are documented as not depending on indexing ("Depends on indexing? No") in the monorepo feature table. A Neovim pyright/basedpyright setup therefore loses little navigation accuracy from having no index. It gains accuracy from correct import roots.
- For a src-layout or multi-package repo in Neovim, the most effective portable config is in-repo `[tool.pyright]`/`[tool.basedpyright]` with `executionEnvironments` (+ `extraPaths`, globbed if needed). Use path-based editable installs (uv workspaces with `uv_build`, or `editable_mode = "compat"`). This configuration is shared with CLI/CI and Pylance users.

### Gaps
- The pyright release that added `extraPaths` glob expansion and the "add on top of default excludes" behavior could not be pinned. Both appear in current `main` docs, and older pyright replaced the default excludes when `exclude` was set (training-data knowledge, not re-verified). Treat both as recent.
- No published memory/scale benchmarks for pyright or basedpyright comparable to Pylance's heap table were found.
- Pylance's Python Environments integration for `usePerProjectEnvironments` has no LSP equivalent in pyright/basedpyright other than one server per root, or `executionEnvironments`, which share one interpreter.

## Interpreter / venv detection

### Takeaway
In VS Code, the Python Environments extension (Rust "PET" scanner) discovers venv/uv/conda/pyenv/poetry/pipenv environments and auto-selects a workspace `.venv` first. Pylance consumes that selection via an extension API. pyright alone uses `venvPath`+`venv` → `python.pythonPath` → `python` on PATH. basedpyright adds `./.venv` auto-detection (v1.25.0, Jan 2025), which closes most of the gap in Neovim.

### Cited Findings
- Python Environments auto-discovery: venv in workspace folders (`python-envs.workspaceSearchPaths`, default `["./**/.venv"]`, workspace-level only); System Python (PATH, `/usr/bin`, `/usr/local/bin`, registry); Conda (`conda info --envs`); Pyenv (`$PYENV_ROOT/versions` or `~/.pyenv/versions`); Poetry (project `.venv` and `~/.cache/pypoetry/virtualenvs`); Pipenv (`~/.local/share/virtualenvs`). Discovery uses "the Python Environment Tool (PET) Rust binary" — [VS Code Python environments docs](https://code.visualstudio.com/docs/python/environments)
- Interpreter selection priority: 1 `python-envs.pythonProjects[]`, 2 `python-envs.defaultEnvManager` (only if explicitly set; default `ms-python.python:venv`), 3 legacy `python.defaultInterpreterPath`, 4 auto-discovery ("workspace-local `.venv`, then global interpreters"). Legacy `python.venvPath`/`python.venvFolders` are merged into the search paths. `python-envs.globalSearchPaths` covers custom dirs. `python-envs.alwaysUseUv` defaults to true — [VS Code Python environments docs](https://code.visualstudio.com/docs/python/environments)
- Pylance "uses the interpreter selected in Python Environments, or the Python extension… when Python Environments is unavailable". Its documented order: explicit choice (`python.defaultInterpreterPath`/workspace state) → venv under the folder (`.venv`, `venv`, `env`, `.env`) → tooling files (`.python-version`/pyenv, `pyproject.toml`/poetry/hatch, `Pipfile`) → conda env for the folder → first on PATH. The interpreter determines `sys.path`/site-packages and the assumed Python version (override with `pythonVersion` in config). "Activating the venv in a terminal does not affect the editor" — [Pylance python-environments how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/python-environments.md)
- pyright's priority: (1) `venv` name + `python.venvPath` (or `--venvpath`), "not recommended for most users"; (2) `python.pythonPath`, which with newer VS Code Python extensions is read "through an API exposed by the Python extension"; (3) the default `python` on PATH — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md)
- `venvPath`/`venv` config keys are "ignored when using Pylance. VS Code's python interpreter path is used instead" — [pyright configuration.md](https://github.com/microsoft/pyright/blob/main/docs/configuration.md)
- basedpyright adds a third step: "If a virtual environment exists in a `.venv` folder at the project root, its python interpreter is used as the default value for `python.pythonPath`" — [basedpyright import-resolution](https://docs.basedpyright.com/latest/usage/import-resolution/); [basedpyright better defaults](https://docs.basedpyright.com/latest/benefits-over-pyright/better-defaults/). Shipped in v1.25.0 (27 Jan 2025). "Allow .venv autodetection when config file missing" followed in v1.28.5 (9 Apr 2025) — [basedpyright releases](https://github.com/DetachHead/basedpyright/releases)
- basedpyright honors only `python.pythonPath` and `python.venvPath` among `python.*` settings. "`python.venvPath` is discouraged in basedpyright" — [basedpyright LS settings](https://docs.basedpyright.com/latest/configuration/language-server-settings/)
- nvim-lspconfig ships `:LspPyrightSetPythonPath <path>` for both `pyright` and `basedpyright`. It sets `settings.python.pythonPath` and sends `workspace/didChangeConfiguration` — [nvim-lspconfig lsp/basedpyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/basedpyright.lua); [nvim-lspconfig lsp/pyright.lua](https://github.com/neovim/nvim-lspconfig/blob/master/lsp/pyright.lua)

### Inferences
- With plain pyright in Neovim, a project `.venv` is only picked up if nvim was launched from an activated venv (so `python` on PATH is the venv's), or if `venvPath`/`venv`/`pythonPath` is set. With basedpyright, `uv`-style `./.venv` at the root works with zero config. Poetry's out-of-tree venvs (`~/.cache/pypoetry/virtualenvs`), conda and pyenv still need `python.pythonPath` (e.g. computed in `before_init`/`on_new_config` from `poetry env info -p` or `$CONDA_PREFIX`).

### Gaps
- No primary doc describes the exact API call Pylance uses to receive the interpreter from Python Environments. Pyright's doc only says "an API exposed by the Python extension".

## Readability features: semantic highlighting, inlay hints, hover/docstrings, outline/breadcrumbs/sticky scroll/folding, CodeLens, Peek

### Takeaway
Pylance's semantic tokens and inlay hints are the biggest readability wins and are absent from upstream pyright. basedpyright re-implements both, with different token names and different inlay defaults: all hint kinds are on by default in basedpyright, off by default in Pylance. Pylance additionally has reST docstring rendering, folding/selection ranges and a docstring-fold command. VS Code's breadcrumbs, outline and sticky scroll come from `documentSymbol`/folding providers, which pyright already supplies (`documentSymbol`).

### Inferences
- Neovim maps LSP semantic tokens to `@lsp.type.<type>.python` / `@lsp.mod.<modifier>.python` groups. With basedpyright you can style `selfParameter`, `clsParameter`, `decorator`, `builtin`/`defaultLibrary`, `readonly` (Final/no-setter properties), `classMember` and `parameter`. Pylance-only distinctions are `module`, `magicFunction`, `typeHint`, `library`, `overridden`, `abstract`, `callable` and `intrinsic`. Plain pyright emits no semantic tokens, so Neovim relies purely on tree-sitter.
- basedpyright's all-on inlay-hint defaults are noisier than Pylance's all-off defaults. A Pylance-like Neovim setup would set `variableTypes=false`, `genericTypes=false`, `callArgumentNames=false` (or keep it) and toggle hints with `vim.lsp.inlay_hint.enable()`.
- Folding and expand-selection for Python in Neovim must come from tree-sitter (`foldexpr=v:lua.vim.treesitter.foldexpr()`, tree-sitter incremental selection). No pyright-family server provides them.
- Outline/breadcrumb equivalents in Neovim (e.g. aerial/outline/navic/dropbar plugins) can use pyright's `documentSymbol`. Sticky-scroll equivalents (treesitter-context) are tree-sitter based.

- The VS Code page fetched did not document Sticky Scroll (`editor.stickyScroll.*`) or which model it uses for Python. Not verified.
- The exact name of Pylance's new "exclude argument names when variable name matches" option (2026.2.106) is not in the README settings list.

## basedpyright: Pylance features re-implemented, defaults, Neovim config, and what remains Pylance-only

### Takeaway
basedpyright (v1.40.2, Oct 2026) re-implements most LSP-visible Pylance features. It does not re-implement type hierarchy, folding/selection ranges, refactorings (extract/move), pytest support, string-literal navigation, Django/Pydantic plugins, docstring-format rendering or the indexer/language-server modes. In Neovim it is configured under `settings.basedpyright.analysis.*` (not `python.analysis.*`) and defaults to strict-ish `recommended` checking.

### Cited Findings
- Documented Pylance re-implementations: Jupyter notebook support (and CLI checking of `.ipynb`); import-suggestion **code actions** (pyright only offers import completions); `# pyright: ignore` code actions; semantic highlighting; inlay hints; docstrings for compiled builtin modules; renaming packages/modules updates usages; multi-line docstring parameter parsing fix; `autoFormatStrings` (f-string on `{`, default true); hover and go-to-definition on operators; Go to Implementations — [basedpyright Pylance features](https://docs.basedpyright.com/latest/benefits-over-pyright/pylance-features/)

### Inferences
- Switching a Neovim config from pyright to basedpyright is mostly a rename of the settings namespace (`python.analysis.*` → `basedpyright.analysis.*`; `pyright.disableTaggedHints` → `basedpyright.disableTaggedHints`). ## Known limitations and complaints: go-to-definition landing in the wrong place, and official workarounds

### Takeaway
Most wrong-place jumps come from five sources: stub-only symbols (both commands land in `.pyi`), overloads (multiple targets), unresolvable dynamic attributes (Django ORM, `__getattr__`, `create_model`, custom decorators), import-hook editable installs, and per-workspace-folder program boundaries. The official workarounds are stubs in `stubPath`/`typings`, `dataclass_transform`, framework stub packages, path-based editable installs, `extraPaths`/`executionEnvironments`, and, Pylance-only, the experimental Django/Pydantic support.

### Cited Findings
- Stub-only → `.pyi`: when only a stub exists (stub-only package, compiled module), both definition and declaration open the `.pyi`. A June 2024 report had go-to-def on `logging.getLogger` landing in the bundled typeshed stub. Pylance added a notification for the fallback in 2026.3.102 — [pylance-release#5007](https://github.com/microsoft/pylance-release/issues/5007)
- Re-exports: pyright follows alias chains to the original declaration (`resolveAliasDeclaration`) — [pyright definitionProvider.ts](https://github.com/microsoft/pyright/blob/main/packages/pyright-internal/src/languageService/definitionProvider.ts). Eric Traut: imported symbols in `__init__.py` are private to the module by default. To re-export, add them to `__all__` or use the redundant form `from x import y as y` — [pylance-release#5872](https://github.com/microsoft/pylance-release/issues/5872)
- Aliased imports and stubs: "Unable to show docstrings and source using aliased import and stub file" was fixed in 2025.12.102. Auto import not suggesting stdlib re-exports was fixed in 2026.1.100 — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Decorators: "Unannotated decorators are now treated as no-ops, rather than using type inference and potentially obscuring the signature of the function they decorate" (Pylance 2021.6.0). The following fixes also landed: "Special-case functools.wraps decorator support" (2025.12.102, 28 Jan 2026), "Function Docstrings Obscured By Decorators That Return Protocols" (2026.1.100), "inherit all decorators when override a member" (2026.1.100) and docstrings of overloads lost through a decorator (2026.2.102) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Dynamic `__init__` assignment (`__init__ = __init_impl`) not followed: fixed in 2026.4.100 prerelease (#8238) — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Django: install `django-stubs` (plus maybe `django-stubs-ext`). Write custom stubs under `stubPath` for uncovered dynamic fields. Or enable `python.analysis.enableDjangoSupport` (experimental; trusted workspace; Windows x64/ARM64, macOS Apple Silicon, Linux x64/ARM64; silently ignored elsewhere) for `objects`, reverse relations and field descriptors. Experimental Django support work: ORM autocompletion (2026.2.100), "improved support for django" (2026.3.100), `urlpatterns` completion (2026.3.100), reverse FK with app-label string target (2026.3.103) — [Pylance generated-code how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/generated-code.md); [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Pydantic: v2 ships `py.typed`, so `BaseModel` fields and validators work natively. `response_model=` on FastAPI routes is not statically checked, so use return annotations. `pydantic.v1` validators may not be recognized. Dynamic `create_model` is covered only by Pylance's experimental `enablePydanticSupport` ("Support for Pydantic dynamic models", 2026.4.100 prerelease; README: "not available in Pylance 2026.4.1") — [Pylance generated-code how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/generated-code.md); [Pylance README](https://github.com/microsoft/pylance-release/blob/main/README.md); [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- SQLAlchemy: 2.0 `Mapped[]`/`mapped_column()` are recognized natively. 1.4 needs `sqlalchemy2-stubs`, which must be removed before upgrading to 2.0 — [Pylance generated-code how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/generated-code.md)
- `__getattr__`/`__getitem__` dynamic attributes: "Pylance cannot infer what attributes are available". Type the dunder in a stub (`typings/<pkg>/__init__.pyi`) or list the attributes explicitly. For custom decorators that synthesize dataclass-like fields, add `@dataclass_transform()` to the decorator's stub — [Pylance generated-code how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/generated-code.md). basedpyright's "Infer code completion of `__getattr__`" (#1700) is open — [basedpyright pylance-parity issues](https://github.com/DetachHead/basedpyright/issues?q=is:issue+is:open+label:%22pylance+parity%22)
- Protobuf/gRPC: generate `.pyi` with `mypy-protobuf` (`--mypy_out`) and add the output dir to `extraPaths` — [Pylance generated-code how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/generated-code.md)
- Unresolved/cross-package targets: go-to-definition requires the target module to be reachable via `extraPaths`, an editable install `.pth`, `executionEnvironments[].extraPaths` or site-packages. In multi-root it is per-folder only — [Pylance monorepo how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/monorepo-setup.md). The wrong interpreter is the most common cause ("If the Python extension and Pylance disagree, Pylance loses") — [Pylance python-environments how-to](https://github.com/microsoft/pylance-release/blob/main/docs/howto/python-environments.md)
- Symlinks: "[Linux] GoTo definition performs symlink resolution" (2023.11.102, #5136). `extraPaths` with symlinked dirs fixed in 2025.8.2. Symlinked-dir re-resolve fixed in 2026.3.102 — [Pylance CHANGELOG](https://github.com/microsoft/pylance-release/blob/main/CHANGELOG.md)
- Debugging import resolution in pyright/basedpyright: set `"verboseOutput": true` in config or pass `--verbose` — [pyright import-resolution.md](https://github.com/microsoft/pyright/blob/main/docs/import-resolution.md). Pylance: `"python.analysis.logLevel": "Trace"` — [Pylance TROUBLESHOOTING](https://github.com/microsoft/pylance-release/blob/main/TROUBLESHOOTING.md)

### Inferences
- In Neovim with basedpyright, the stub-only case behaves like Pylance's, minus the notification. If `gd` lands in a `.pyi`, it is because no source mapping exists (compiled or stub-only), not a config bug. `useLibraryCodeForTypes` and an installed source package are prerequisites for source jumps.
- The Django/Pydantic metaprogramming gaps cannot be closed in pyright/basedpyright except through stub packages (`django-stubs`, `django-types`), hand-written stubs and `dataclass_transform`. Pylance's experimental support depends on a native binary and is VS Code-only.

### Gaps
- No primary-source list of pyright/basedpyright GitHub issues was found that specifically documents go-to-definition on decorated functions landing on the decorator or wrapper. Evidence is limited to Pylance changelog fixes for hover/docstrings through decorators.
- Pylance's specific Find References behavior for `@property` setters, `TypedDict` keys and `NamedTuple` fields was not investigated.
